# 本地 Git 多账号管理器 · 初步规划设计

> 来源：思源笔记《多个Github账号长期稳定使用》（编程学习 / Git）
> 状态：技术栈与范围已确认；新增加密工作空间与云同步设计（见 §4、§5）

---

## 1. 这个软件要解决什么

笔记里那套「方案 B（SSH 多账号）」流程本身是对的，但它是一串**必须按顺序手敲、且错一步就沉默失败**的命令。把笔记逐条翻译成痛点：

| 笔记步骤 | 手工做的时候会出什么问题 |
|---|---|
| 2) `ssh-keygen` 生成密钥 | 保存路径要手输绝对路径，输错就生成到当前目录；命名全靠自觉；密码短语记在笔记里 |
| 3) 启用 ssh-agent + `ssh-add` | 要管理员 PowerShell、要记得设开机自启；每加一次都要重新敲一遍口令 |
| 4) 复制公钥到 GitHub | `Get-Content xxx.pub` 输出后手动全选复制，容易漏字符或带上换行 |
| 5) 编辑 `~/.ssh/config` | 最容易错的一步：漏 `IdentitiesOnly yes` 会导致 agent 拿第一把 key 去试；Windows 路径反斜杠 / `~` 混用；Host 重名；缩进 |
| 6) `ssh -T` 验证 | 要人眼去读返回的 `Hi <账号名>`，判断是不是自己想要的那个账号 |
| 7)(9) clone / `remote set-url` | 忘了把 `github.com` 换成别名 `github-new`，于是又走回默认账号 |
| 8) 设置提交身份 | 经常忘设，导致提交记录挂在错误的邮箱上，事后要 rebase 改历史 |
| 清理命令 | config 里的 `IdentityFile` 指向已删除的文件（孤儿条目），agent 里残留 key，只能靠 `ssh-add -l` 和 `Select-String` 人工比对 |

所以产品的一句话定位是：

> **把「一个 Git 身份」当成一个可管理的对象**——密钥、SSH 别名、agent 加载状态、提交身份、以及哪些本地仓库在用它，全部收拢到一个界面里，并能一键体检和修复。

除此之外还有第二个目标——**这些密钥资产本身也需要被安全地保管和备份**。密钥丢了（换电脑、重装、磁盘坏）意味着所有账号都要重新配一遍；密钥泄露则意味着所有仓库的写权限外流。所以应用自带一个加密工作空间（§4）和端到端加密的云备份（§5）。

### 非目标（明确不做）

- 不做 Git 客户端（不替代 Fork / SourceTree / IDE 内置 Git），不做提交、分支、合并
- 不做自建服务端。云同步只把加密后的字节丢进用户自己的 R2 / S3 存储桶，我们不运营任何服务、不持有任何用户数据
- 不接管用户手写的 `~/.ssh/config` 内容（只在自己的托管区块内改写，见 §6.3）

## 2. 核心概念模型

整个应用围绕一个实体：**身份（Identity）**。

```
Identity
├── 名称           "juice520（个人主号）"
├── 平台           github / gitlab / gitee / 自建
├── SSH Host 别名  github.com  或  github-techn
├── 真实主机       github.com  /  ssh.boxexchanger.net
├── 密钥对         C:\Users\juice\.ssh\id_ed25519_juice (+ .pub)
│   ├── 类型/指纹  ed25519, SHA256:xxxx
│   ├── 有无口令
│   └── 文件权限   Windows ACL 是否收紧
├── 提交身份       user.name / user.email
├── 归属标识       该身份名下的 owner 列表（账号名 + 所属组织）
│                  如 techn4950、vortaq-trad、mgcp-afk，支持通配符
├── 运行时状态     agent 是否已加载 / ssh -T 实测到的账号名
└── 关联仓库       扫描出来的本地仓库列表
```

一个身份对应 config 里的一段：

```
Host github-techn
    HostName github.com
    User git
    IdentityFile C:\Users\juice\.ssh\id_ed25519_techn
    IdentitiesOnly yes
```

界面上所有操作都是对这个对象的增删改查，用户不需要知道底下拼了什么命令（但要能看到，见 §6.6）。

身份之上还有一层容器——**工作空间（Workspace）**，即所有身份、密钥和机密的加密存放地，详见 §4。

## 3. 功能模块

### 3.1 身份总览（主界面）

卡片或表格列出所有身份，每张卡片直接给出四个状态灯：

- **密钥**：文件存在 / 缺失 / 权限过宽
- **配置**：config 中已写入 / 缺失 / 与实际不符
- **Agent**：已加载 / 未加载
- **连通**：`ssh -T` 上次实测结果，绿色显示 `Hi techn4950`，红色显示失败原因

点任意一个红灯，给出「一键修复」而不是只报错。这是整个产品最主要的价值点。

### 3.2 新建身份向导

把笔记的步骤 2→3→4→5→6 压缩成一个五步向导：

1. **填信息**：平台、备注名、邮箱、Host 别名（自动建议 `github-<备注名>`，实时检测重名）
2. **密钥**：新建（ed25519 默认，路径按 `id_ed25519_<备注名>` 自动命名）或导入已有文件（见 §4.6）；口令默认由应用生成强随机值并存入 vault，用户全程无感
3. **上传公钥**：显示公钥 + 一键复制 + 直达 GitHub SSH keys 设置页的按钮；配置了 PAT 时可直接调 API 上传（见 §8）
4. **验证**：自动写 config、`ssh-add`、跑 `ssh -T`，把返回的账号名和用户填的备注名比对后展示结果
5. **归属标识**：录入这个身份名下有哪些 owner（见 §3.9）。放在验证之后是有意为之——此时 `ssh -T` 已经拿到真实账号名，可以自动填上第一条

### 3.3 密钥管理

- 列出 `~/.ssh` 下所有密钥对（以及 config 里引用到的、不在该目录的外部路径，比如笔记里那个 `D:\...\git-ssh\vchangr-box-git-ssh`）
- 查看公钥、指纹、类型、创建时间；一键复制公钥
- 修改 / 添加 / 移除口令（`ssh-keygen -p`）
- 删除密钥：删之前强制备份到应用备份目录，并提示"有 N 个身份 / M 个仓库正在用它"
- **Windows 权限修复**：私钥 ACL 过宽时 OpenSSH 直接拒绝使用（`UNPROTECTED PRIVATE KEY FILE`），提供 `icacls` 一键收紧到仅当前用户

### 3.4 SSH config 可视化

- 结构化解析 `~/.ssh/config`，表格展示每个 Host 块
- 表单式编辑，保存前做校验：Host 重名、IdentityFile 路径不存在、缺 `IdentitiesOnly yes`（笔记里第一段 `Host github.com` 恰好就漏了这条，是个典型隐患）
- 提供「原文 / 结构化」双视图，改完先看 diff 再落盘
- 每次写入前自动备份 `config.bak.<时间戳>`

### 3.5 ssh-agent 管理

- 显示 ssh-agent 服务状态与启动类型，一键设为自动启动并启动（对应笔记步骤 3）
- 列出 `ssh-add -l` 的结果，并**按指纹反查**是哪个身份（原生命令只给路径和指纹，看不出是谁）
- 加载 / 卸载 / 清空（`ssh-add` / `-d` / `-D`）
- 口令由 vault 保管，解锁工作空间后加载密钥时自动填入，不再弹窗要口令

### 3.6 连接体检

对所有身份批量跑 `ssh -T`，解析 `Hi <name>!`，做三件事：

- 提取真实账号名，和该身份配置的预期账号比对，不一致直接标红（这能抓出"别名指向了错误的 key"这类最隐蔽的问题）
- 把常见报错翻译成中文人话 + 修复按钮（权限被拒 / 密钥未加载 / Host 未配置 / 主机指纹变更）
- 支持定时或启动时自动体检

### 3.7 本地仓库管理

用户指定一到多个代码根目录（比如 `D:\coding_program`），扫描其中的 Git 仓库，对每个仓库展示：

- `remote origin` 的 URL 及它解析到的 Host 别名
- 仓库级 `user.name` / `user.email`，以及是否与该别名对应的身份一致
- **身份不匹配时一键切换**：同时改 `git remote set-url` 和仓库级提交身份（对应笔记步骤 8、9）

### 3.8 仓库地址智能识别与别名转换

笔记里那句加粗的警告——「**必须**使用 `git@github-new:`（不是 github.com），这样才会走新账号」——是整套方案里最容易犯、也最容易被忽略的错误。因为从 GitHub 网页上复制到的地址永远是 `https://github.com/owner/repo` 或 `git@github.com:owner/repo.git`，**永远不带你的别名**。每次都得手动改，改错了就静默走了默认账号。

这个功能就是彻底消灭这一步：**复制仓库地址 → 应用自动判断该用哪个身份 → 直接给出改写好的地址**。

#### 输入：能认出各种形态的地址

用户复制过来的东西五花八门，都要能解析：

| 来源 | 形态 |
|---|---|
| 网页 Code 按钮（HTTPS） | `https://github.com/owner/repo.git` |
| 网页 Code 按钮（SSH） | `git@github.com:owner/repo.git` |
| **浏览器地址栏** | `https://github.com/owner/repo/tree/main/src`、`/blob/...`、`/pull/123`、`/issues` |
| 已是别名形式 | `git@github-new:owner/repo.git`（识别出来后校验别名是否仍有效） |
| 裸简写 | `owner/repo` |
| gh CLI | `gh repo clone owner/repo` |
| 带端口的 SSH | `ssh://git@host:2222/owner/repo.git` |
| 自建服务 | `git@ssh.boxexchanger.net:bx4/vchangr-com/exchanger-client-web.git` |

浏览器地址栏那一行是重点：实际使用中人们经常直接从地址栏复制，粘到终端里才发现 clone 不了。应用要能从 `/tree/main/src` 这类路径里正确剥出 `owner/repo`。

#### 核心：身份推断

拿到 `host + owner + repo` 之后，按置信度从高到低依次判断，**第一个命中的作为推荐项，其余作为备选列出**：

| 依据 | 说明 | 置信度 |
|---|---|---|
| **归属标识精确匹配** | owner 已登记在某身份名下（见 §3.9）。这是**用户显式声明的意图**，压过一切启发式规则 | 确定 |
| **归属标识通配匹配** | owner 命中某身份登记的通配规则，如 `vortaq-*` | 很高 |
| **主机唯一匹配** | host 是 `ssh.boxexchanger.net`，而只有一个身份配了这台主机 | 确定 |
| **owner 等于账号名** | owner 正好是某身份 `ssh -T` 实测到的真实账号名 | 很高 |
| **历史记录** | 以前用某身份克隆过同一个 owner 下的仓库 | 中高 |
| **API 查询归属** | 有 PAT 时实时查该账号是否为这个 org 的成员 | 高（但需联网） |
| **实测权限探测** | 用候选身份跑 `git ls-remote`，能读到引用就说明有权限 | 很高（但慢） |
| **默认身份** | 都没命中时的兜底，并明确提示"未能自动识别" | 低 |

前两条命中时，整个判断是**纯本地查表，零网络请求，瞬间出结果**——这正是提前录入归属标识的价值。后面几条是没登记过的 owner 才会走到的回退路径。

`git ls-remote` 这个兜底手段值得单独说：它不需要真的克隆，几百毫秒就能确认某个身份对某个仓库到底有没有读权限，对**私有仓库**尤其有效（无权限的身份会直接失败，等于做了一次判定）。为避免打扰，它只在前面所有规则都无法给出高置信度结论时才触发。

#### 输出：给出结果和依据

界面上呈现三样东西：

1. **改写后的地址**，一键复制：`git@github-techn:owner/repo.git`
2. **推断依据**，明写出来，比如「owner `vortaq-trad` 匹配身份 *techn4950* 的历史克隆记录」——不能只给结论，用户要能判断这个推断对不对
3. **一键操作**：直接克隆（选目标目录，克隆完自动写入该仓库的 `user.name` / `user.email`），或仅复制地址自己去终端执行

若推断不确定，界面上并列展示所有候选身份让用户选，并把这次选择记进规则表，下次同 owner 直接命中。

#### 剪贴板感知（可选，默认关闭）

开启后，应用检测到剪贴板出现 Git 仓库地址时，弹出一个轻量通知：「检测到 `owner/repo`，建议用身份 *techn4950* → 点击克隆 / 复制别名地址」。

这是最贴近"复制完就能用"的形态，但**剪贴板监听是隐私敏感行为**，所以：默认关闭、需用户显式开启、只匹配 Git 地址正则、不记录任何其他剪贴板内容、匹配失败的内容立即丢弃不留痕。

#### 反向能力：地址体检

同一套解析和推断逻辑复用到 §3.7 的仓库扫描上——扫描到某个本地仓库的 remote 用的是 `github.com` 而非别名时，判断它"本应"属于哪个身份，直接给出 `git remote set-url` 的修复建议。这正是笔记步骤 9 要手工做的事。

### 3.9 归属标识：让识别从"猜"变成"查表"

仓库地址里的 owner 段本身就是最强的身份信号——`vortaq-trad/vq-officail`、`mgcp-afk/xxx`，看一眼就知道该用哪个账号。既然用户自己清楚这个对应关系，就不该让程序去猜，**在创建身份时直接登记下来**。

#### 数据形态

每个身份挂一组归属标识：

```
身份「techn4950」
├── techn4950        （账号名，ssh -T 验证后自动写入）
├── vortaq-trad      （组织）
├── mgcp-afk         （组织）
└── vortaq-*         （通配规则，覆盖未来新建的同前缀组织）
```

三点设计约束：

- **大小写不敏感**：GitHub 用户名不区分大小写，统一转小写后比对
- **支持通配符**：像 `vortaq-trad`、`mgcp-afk` 这种带固定前缀的命名，登记一条 `vortaq-*` 就能覆盖以后新建的组织，不用每次补录
- **owner 不一定只有一段**：笔记里那个 `git@git-box:bx4/vchangr-com/exchanger-client-web.git` 是三段路径——自建 Gitea / GitLab 支持嵌套 group。所以归属标识匹配的是**仓库路径前缀**而非单个路径段，`bx4/vchangr-com` 可以整体登记为一条

#### 三种录入方式，尽量不让用户手打

1. **手动录入**：向导第 5 步直接填，支持一行一个批量粘贴
2. **`ssh -T` 自动获取**：验证连接时返回的 `Hi <账号名>` 就是一条归属标识，自动写入。这一条不需要任何额外配置
3. **PAT 一键拉取**（推荐）：配了 token 的话，调 `GET /user` 拿账号名、`GET /user/orgs` 拿该账号所属的**全部组织**，列出来让用户勾选后批量导入

第三种是最省事的——你不用记得自己在哪些组织里，应用直接列给你。GitLab 对应 `GET /groups`，Gitea 有等价接口。

#### 自动学习与回填

登记表不是一次性的，日常使用中持续自我完善：

- 克隆或扫描时遇到**未登记的 owner**，在用户选定身份后，弹一个轻量提示：「把 `vortaq-trad` 登记到身份 *techn4950* 名下？以后自动识别」——一次点击，下次就是查表命中
- 扫描本地仓库时批量发现新 owner，汇总成一个待确认列表，一次性处理完
- 若某 owner 连续多次被手动指向同一身份却始终没登记，主动提醒

#### 冲突处理

同一个 owner 被两个身份同时声明是**合法场景**——比如你的工作号和个人号都加入了同一个组织。所以不能简单地禁止，而是：

- 界面上把冲突的 owner 标出来，让用户指定其中一个为**优先身份**
- 或者标记为"每次询问"，遇到该 owner 时并列展示两个候选
- 也可以用 `git ls-remote` 对两个身份实测消歧（有些仓库只有其中一个账号有权限）

精确匹配永远优先于通配匹配，所以 `vortaq-*` 归 A 身份、`vortaq-trad` 单独归 B 身份这种细化配置能正常工作。

## 4. 加密工作空间

### 4.1 为什么需要它

到目前为止的设计有个隐含前提：密钥散落在 `~/.ssh` 和各种项目目录里（笔记里那把 `D:\codeProgrammer\makeMoney\vchangr\box-exchanger\git-ssh\vchangr-box-git-ssh` 就是典型）。这带来两个问题：

- **丢**：换电脑、重装系统、磁盘损坏，所有账号都要重配一遍
- **漏**：散落的私钥不知道权限对不对、有没有被同步盘（OneDrive / 坚果云）顺手上传、有没有被误提交进某个仓库

所以引入**工作空间**：一个由用户指定的目录，作为所有密钥资产的**权威副本（source of truth）**，内容全部加密存放。`~/.ssh` 降级为"投放目标"——由工作空间生成，坏了可以随时重建。

### 4.2 初始化流程

首次启动时的一次性向导，五步：

1. **选择工作空间目录**——建议选一个不被任何同步盘接管的本地目录（应用会检测路径是否位于 OneDrive / Dropbox / 坚果云等目录下并警告，因为端到端加密的备份应该走 §5 的通道，而不是让同步盘拿到整个目录）
2. **设置访问密码**——日常解锁用，有强度指示器
3. **生成并展示恢复密钥**——只在此刻显示一次
4. **强制回填校验**——随机抽查恢复密钥中的两组字符，让用户填回来。这是为了确保用户**真的**抄写/保存了，而不是随手点掉"我已保存"
5. **导入已有密钥**（可跳过）——见 §4.6

### 4.3 密钥体系

采用**信封加密（envelope encryption）**，三层结构：

```
        访问密码                      恢复密钥（256-bit 随机）
           │                                │
    Argon2id(慢哈希，抗暴力)          HKDF-SHA256(已是高熵，无需慢哈希)
           │                                │
        KEK_pwd                          KEK_rec
           │                                │
           └──────┐              ┌──────────┘
        各自 AEAD 加密同一把主密钥
                  ▼              ▼
              ┌─────────────────────┐
              │  主密钥 MK (256-bit) │  ← 只在解锁期间存在于内存
              └─────────────────────┘
                          │
              HKDF(MK, 用途标签) 派生子密钥
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   私钥文件加密       元数据加密        云对象名 HMAC
```

关键点：**主密钥只有一把，但有两个信封**。访问密码和恢复密钥各自能解开同一把 MK。由此得到三个重要性质：

- **改密码是毫秒级操作**——只需用新密码重新包裹 MK，不用重新加密工作空间里的任何数据
- **恢复密钥可以轮换**——在已解锁状态下重新生成一把，作废旧的
- **两个都丢 = 数据永久无法恢复**——没有后门，这一点必须在初始化时用最醒目的方式告诉用户

算法选型：

| 环节 | 算法 | 参数 / 说明 |
|---|---|---|
| 密码派生 | Argon2id | 运行时按机器标定到约 500ms（参考机为 256MiB/3/4，见 M0 结论）；OWASP 下限 19MiB/2 兜底；参数存头部便于升级 |
| 恢复密钥派生 | HKDF-SHA256 | 恢复密钥本身已有 256-bit 熵，不需要慢哈希 |
| 对称加密 | XChaCha20-Poly1305 | 24 字节 nonce 可安全随机生成，无需维护计数器；AEAD 自带完整性校验 |
| 随机数 | OS CSPRNG | `getrandom`，不使用任何伪随机 |

### 4.4 恢复密钥的形态

256-bit 随机数，用 Crockford Base32 编码（去掉 `I` `L` `O` `U`，避免手抄时和 1 / 0 混淆），带版本前缀和校验组：

```
GAM1-K7X2-9MQR-4TWB-8FHV-3NCD-6JYP-2SZG-5LKA-7RXE-9BTM-4WQF-H3N8
```

配套的体验设计：

- 展示时提供：复制、导出为 txt、生成二维码（方便拍照存到离线设备）、直接打印
- 输入时逐组校验，抄错立刻标红到具体某一组，而不是最后统一报"密钥错误"
- 大小写不敏感、自动忽略连字符和空格
- 之后可在已解锁状态下重新查看（需二次输入访问密码），但界面要写明这是"再看一次"，不是"找回"——真忘了没人能找回

### 4.5 私钥落盘这个绕不开的矛盾

**问题**：`ssh` 和 `ssh-add` 只能读取磁盘上的私钥文件。工作空间里加密得再好，用的时候还是得有个文件让 OpenSSH 读——那加密的意义在哪？

这个矛盾必须正面回答，有两条互补的解法：

**解法一：私钥文件本身就是加密的（默认）**

OpenSSH 私钥带口令时，文件内容本身就是用 bcrypt-pbkdf 派生密钥后 AES 加密的密文。也就是说，只要**强制每把私钥都有口令**，`~/.ssh` 下的所谓"明文私钥"其实并不明文。而口令由 vault 保管、自动填入 agent，用户完全无感。

因此产品上做一条硬规定：**通过本应用创建的密钥一律带随机强口令**；导入的无口令密钥会被标黄，并提供一键加口令。

**解法二：磁盘上只留公钥，私钥只活在 agent 内存里（严格模式，可选）**

一个不太为人知的 OpenSSH 特性：`IdentityFile` 可以指向 `.pub` 公钥文件。ssh 会读取公钥、拿它去 agent 里找对应的私钥来签名。也就是说：

```
Host github-techn
    HostName github.com
    User git
    IdentityFile C:\Users\juice\.ssh\id_ed25519_techn.pub   ← 只有公钥
    IdentitiesOnly yes
```

配合这个特性，严格模式的工作方式是：解锁 vault → 解密私钥到内存 → 直接喂给 ssh-agent → **私钥明文从未落盘**，磁盘上只有 `.pub`。关掉应用或锁定时从 agent 卸载。

代价是每次开机要先解锁一次应用，agent 才有 key。所以它是可选项而不是默认。

> **M0 已验证此路径可行**（见 `docs/M0-技术验证结论.md`）：`ssh-add -` 可从 stdin 加载私钥（agent 来源显示 `(stdin)`，磁盘无文件）；`IdentityFile` 指向 `.pub` 时 ssh 会匹配 agent 中的私钥（日志 `Offering public key ... explicit agent`）。两者结合，私钥明文全程不落盘的严格模式成立。

### 4.6 从外部导入密钥对

导入是把散落的密钥收拢进工作空间的入口，也是老用户的第一步。

**支持的来源**

- 单个文件：选私钥，自动在同目录找同名 `.pub`；找不到就用 `ssh-keygen -y` 从私钥推导公钥（需要口令）
- 批量扫描：扫 `~/.ssh` 以及 `config` 里所有 `IdentityFile` 引用到的路径——这一步正好能把笔记里那把散在 `D:\codeProgrammer\...` 的密钥收进来
- 拖拽文件夹、粘贴私钥文本

**格式处理**

| 格式 | 处理方式 |
|---|---|
| OpenSSH（`-----BEGIN OPENSSH PRIVATE KEY-----`） | 原生支持 |
| 传统 PEM（RSA / EC） | 支持，并建议转成 OpenSSH 新格式 |
| PuTTY `.ppk` | 检测到后提示转换（`puttygen -O private-openssh`），因为 OpenSSH 不认这个格式——用过 Xshell / PuTTY 的用户很容易踩这个坑 |

**导入时做的校验**

1. 解析私钥，确认格式合法、识别类型（ed25519 / rsa / ecdsa）
2. 如果带口令，要求用户输入——既是验证口令正确，也是把它存进 vault 的唯一机会
3. **验证公私钥确实配对**（从私钥推导公钥再比对），防止导入一对张冠李戴的文件
4. 计算指纹，与已导入的密钥查重
5. RSA 密钥若小于 2048 位则警告

**原文件如何处理**（导入完成后询问，默认第一项）

- **保留原文件**，工作空间里存一份加密副本——最安全，适合不确定的时候
- **移入工作空间**，原文件安全擦除（多次覆写后删除）——适合想彻底收拢的场景，会二次确认
- **保留但收紧权限**——原地 `icacls` 修复 ACL

### 4.7 工作空间的目录结构

```
<工作空间>/
├── vault.json              # 头部：版本、KDF 参数、两个信封。不含任何明文机密
├── data/
│   ├── identities.enc      # 身份元数据（名称、别名、邮箱、平台……）
│   ├── secrets.enc         # 密钥口令、GitHub PAT、R2/S3 凭据
│   └── settings.enc        # 应用设置
├── keys/
│   └── <keyId>.enc         # 私钥的加密权威副本
├── backups/                # 本地历史快照
├── sync/
│   └── manifest.enc        # 云同步索引（对象名映射、版本、哈希）
└── audit.log               # 操作日志（脱敏，不加密，便于出事后排查）
```

`vault.json` 是唯一不加密的文件，但它只有这些内容：

```json
{
  "version": 1,
  "workspaceId": "3f9a...",
  "createdAt": "2026-09-08T15:00:00Z",
  "kdf": { "algo": "argon2id", "memKiB": 65536, "iters": 3, "parallelism": 4 },
  "envelopes": {
    "password": { "salt": "<b64>", "nonce": "<b64>", "wrappedKey": "<b64>" },
    "recovery": { "salt": "<b64>", "nonce": "<b64>", "wrappedKey": "<b64>" }
  }
}
```

没有校验值字段——AEAD 解包失败本身就说明密码错了，不需要额外给攻击者一个离线校验的靶子。

### 4.8 访问密码与锁定（参考思源笔记）

思源的「访问授权码」+「自动锁屏」是很合适的参照，但有一个本质区别必须讲清楚：

> 思源的授权码是**访问控制**——数据在磁盘上是明文的，改配置文件就能绕过。
> 本应用的访问密码是**加密密钥的来源**——没有它（或恢复密钥）就是一堆无法解开的密文，谁也绕不过，包括开发者。

所以对应的设计是：

- **访问密码**：解锁工作空间。首次初始化时设置，可在设置里修改（改密码只重新包裹 MK，不重新加密数据）
- **自动锁定**：默认 15 分钟无操作后锁定；可选"系统休眠 / 锁屏时立即锁定"、"窗口最小化时锁定"；可设为永不（有风险提示）
- **手动锁定**：标题栏按钮 + 全局快捷键
- **锁定的语义是真锁**：MK 及所有派生密钥从内存清零，不是遮一层界面
- **暴力破解防护**：连续失败后递增延迟（1s → 2s → 4s …），10 次后强制冷却。Argon2id 本身已经让离线爆破极其昂贵，这一层是防手动试探
- **可选：Windows Hello 快速解锁**——把 MK 用 DPAPI 加密后存进凭据管理器，绑定当前 Windows 账户，用指纹 / PIN 解锁。这是**便利性**功能，安全性取决于 Windows 账户，默认关闭

### 4.9 内存与旁路防护

- 所有密钥材料用 `zeroize` 包装，离开作用域自动清零
- 尝试 `VirtualLock` 防止 MK 被换页到 pagefile（尽力而为，Windows 有配额限制）
- 明文私钥、口令、token **永不进入日志**，日志层做统一脱敏
- 前端只接收"是否已解锁""指纹""公钥"这类信息，**私钥明文和口令绝不跨 IPC 传到 WebView**——需要私钥的操作全部在 Rust 侧完成
- 剪贴板写入敏感内容后，60 秒自动清除

## 5. 云同步（端到端加密）

### 5.1 定位

**这不是实时协作同步，而是加密异地备份 + 换机恢复。** 目标场景只有两个：磁盘坏了、换新电脑。刻意不做双向实时同步，因为它会引入冲突合并的复杂度，而密钥数据一旦合并错就是灾难。

### 5.2 关于"不能上传明文公钥"

先澄清一个技术事实，因为它影响设计边界的判断：公钥本身在密码学上是公开信息，任何人访问 `github.com/<用户名>.keys` 就能拿到你所有的 GitHub 公钥。

但你的直觉是对的，只是敏感点不在公钥内容，而在**关联元数据**——这份数据一旦明文躺在云上，泄露的是"这台机器的主人拥有哪几个账号、账号之间的对应关系、用了哪些自建服务器（比如 `ssh.boxexchanger.net`）、本地有哪些项目"。这种关联信息比公钥本身敏感得多。

所以结论一致：**整个数据集全量加密上传，服务端零知识**。包括公钥、包括元数据、也包括对象名本身。

### 5.3 加密模型

- 上传前用 `HKDF(MK, "sync-object")` 派生的密钥做 XChaCha20-Poly1305 加密，**云端只见密文**
- **对象名也不能泄露信息**。不能出现 `keys/id_ed25519_techn.enc` 这种名字——它直接暴露了账号名。改用 `HMAC-SHA256(HKDF(MK, "sync-name"), 逻辑路径)` 的十六进制值作为对象 key，云端看到的只是一堆无意义的哈希
- 索引由加密的 `manifest.enc` 维护，记录逻辑路径 → 对象名 → 版本 → 内容哈希的映射
- 用**填充**把对象大小归整到固定档位，避免通过文件大小推断内容类型
- R2 / S3 的 access key 本身是机密，存在 vault 里，跟着一起加密

### 5.4 存储后端

抽象成一个 trait，S3 兼容协议一套代码覆盖两家：

```rust
trait SyncBackend {
    async fn put(&self, key: &str, data: &[u8], if_match: Option<&str>) -> Result<String>;
    async fn get(&self, key: &str) -> Result<(Vec<u8>, String)>;  // 内容 + ETag
    async fn list(&self, prefix: &str) -> Result<Vec<ObjectMeta>>;
    async fn delete(&self, key: &str) -> Result<()>;
}
```

首批实现 Cloudflare R2 和 AWS S3（R2 兼容 S3 API，差异主要在 endpoint 和区域），后续可加 MinIO、阿里云 OSS、腾讯云 COS。用 `aws-sdk-s3` 或直接用 `reqwest` + 手写 SigV4 签名。

配置界面需要：endpoint、bucket、access key id、secret access key、region、路径前缀，外加一个**连接测试**按钮（试写一个探针对象再删掉，验证读写删权限齐全）。

### 5.5 冲突与一致性

- 每个对象带单调递增版本号，写入用条件请求（`If-Match` ETag）实现乐观并发
- **检测到冲突时绝不自动合并**，停下来让用户选择保留哪一侧，并把另一侧存为快照
- manifest 采用"先传数据对象、再传 manifest"的顺序，保证 manifest 永远指向已存在的对象；中途失败最多留下几个孤儿对象，由垃圾回收清理，绝不会出现索引指向不存在对象的损坏状态
- 云端保留最近 N 个版本，防止本地误删后同步上去导致两边都没了

### 5.6 换机恢复流程

新电脑上：安装应用 → 选"从云端恢复" → 填 R2 / S3 连接信息 → **输入恢复密钥** → 拉取并解密 manifest → 选择要恢复的身份 → 还原密钥文件、重建 `~/.ssh/config`、修复权限 → 设置新的访问密码。

这里恢复密钥是**唯一**能解开数据的东西（新机器上没有凭据管理器里的任何东西），所以初始化时对它的强调怎么强调都不过分。

## 6. 技术设计

### 6.1 技术栈（已确认）

**Tauri 2 + React + TypeScript（前端）/ Rust（后端）**，桌面窗口应用，不常驻托盘。

选它的核心理由：这个应用**大量操作本地文件权限和外部进程**，Rust 侧做这些既安全又不需要额外原生模块；同时体积和常驻内存对一个「偶尔打开用一下」的工具很重要（Tauri 约 10MB，Electron 100MB 起）。

预计依赖：

| 用途 | 选型 |
|---|---|
| 前端框架 / 构建 | React 18 + TypeScript + Vite |
| UI 组件 | shadcn/ui + Tailwind（状态灯、表格、向导步骤条都够用） |
| Rust 异步运行时 | tokio |
| 执行外部命令 | `tokio::process`；需要伪终端时用 `portable-pty`（封装 ConPTY） |
| SSH 密钥解析 / 指纹 / 格式转换 | `ssh-key` crate（纯 Rust，同时支持读取带口令的私钥） |
| 密码派生 | `argon2`（Argon2id） |
| 对称加密 | `chacha20poly1305`（XChaCha20-Poly1305） |
| 密钥派生 / HMAC | `hkdf` + `hmac` + `sha2` |
| 内存清零 | `zeroize` |
| 恢复密钥编码 | `base32`（Crockford 变体）+ 自实现校验组 |
| 系统凭据存储 | `keyring` crate（仅用于可选的"Windows Hello 快速解锁"，**不是**机密的主存储） |
| 对象存储 | `aws-sdk-s3`（R2 走 S3 兼容端点），或 `reqwest` + 手写 SigV4 |
| GitHub API | `reqwest` + 手写薄封装（只用到 `POST /user/keys` 等两三个接口） |
| 本地仓库信息读取 | 优先 `git` 命令；只读场景可考虑 `gix` |

### 6.1.1 平台抽象

先做 Windows，但从第一天起把平台相关的操作收在 trait 后面，后续加 macOS / Linux 只需补实现、不动上层逻辑：

```rust
trait PlatformOps {
    fn secure_key_file(&self, path: &Path) -> Result<()>;   // Windows: icacls；Unix: chmod 600
    fn agent_status(&self) -> Result<AgentStatus>;          // Windows: 服务查询；Unix: 检查 SSH_AUTH_SOCK
    fn ensure_agent_running(&self) -> Result<()>;
    fn ssh_dir(&self) -> PathBuf;
    fn locate_ssh_binaries(&self) -> Result<SshToolchain>;  // 区分系统 OpenSSH 与 Git for Windows 自带的
}
```

凭据存储、路径规范化同理。约束：**平台判断只允许出现在这些实现里**，业务代码中不得出现 `cfg!(windows)`。

### 6.2 底层实现方式：调命令 vs 调库

采取**混合策略**：

- **调外部命令**（`ssh-keygen`、`ssh-add`、`ssh -T`、`git`、`icacls`）：与用户在终端里的行为完全一致，不会出现"应用里能用、命令行里不能用"的割裂，也便于把执行的命令原样展示给用户
- **纯 Rust 实现**：config 的解析与生成、指纹计算、公钥读取——这些需要精确控制格式，不适合靠解析命令输出

### 6.3 `~/.ssh/config` 的安全改写策略

这是最容易把用户配置搞坏的地方，必须约定清楚：

1. 应用只在自己的**托管区块**内增删改：

```
# ===== BEGIN managed by git-account-manager =====
Host github-techn
    HostName github.com
    User git
    IdentityFile C:\Users\juice\.ssh\id_ed25519_techn
    IdentitiesOnly yes
# ===== END managed by git-account-manager =====
```

2. 区块外的用户手写内容**原样保留**，包括注释和空行
3. 首次运行时扫描已有 Host，询问用户是否"纳入托管"（把笔记里已有的三段迁进来）
4. 每次写入前备份，且写入采用「临时文件 + 原子替换」，避免写一半崩溃导致 config 损坏
5. 落盘后立刻用 `ssh -G <host>` 反向验证解析结果符合预期

### 6.4 机密的保管位置

所有机密（密钥口令、GitHub PAT、R2/S3 access key）统一存放在**工作空间的加密 vault** 里（§4.7 的 `secrets.enc`），不再依赖系统凭据管理器。

这是相比早期方案的一个改变，原因有三：凭据管理器的内容跟 Windows 账户绑定、**无法跟着工作空间备份到云端**；不同平台实现不一，跨平台行为不一致；而且它对用户是不可见不可审计的黑盒。放进 vault 则天然获得加密、备份、换机恢复三件事。

系统凭据管理器只保留一个用途：可选的"Windows Hello 快速解锁"（存被 DPAPI 保护的 MK 副本，见 §4.8）。

> 顺便提醒：那篇笔记的正文里直接写了一个真实的密钥口令明文。笔记若参与同步或分享，建议尽快把它删掉并给对应密钥换一个口令（`ssh-keygen -p`）——这也正好是本应用要提供的功能之一。

### 6.5 已知技术风险（原型阶段优先验证）

> 下表中带 ✅/⚠️ 的项已在 M0 完成实测，详见 `docs/M0-技术验证结论.md`。

| 风险 | 说明 | 预案 / M0 结论 |
|---|---|---|
| `ssh-add` 的口令输入 | Windows OpenSSH 的 `ssh-add` 从控制台读口令，无法简单地从 stdin 喂 | ✅ `SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force` 已验证可行，无需 ConPTY |
| **私钥不落盘地加载进 agent** | §4.5 严格模式的前提 | ✅ `ssh-add -` 从 stdin 加载成功，agent 来源显示 `(stdin)` |
| **`IdentityFile` 指向 `.pub`** | §4.5 严格模式依赖此特性 | ✅ 已验证：ssh 匹配 agent 私钥（`Offering public key ... explicit agent`） |
| 私钥 ACL | 权限过宽时 OpenSSH 是否拒绝 | ⚠️ icacls 收紧有效，但本机 9.5p2 **不强制拒绝**；icacls 作主动加固，不依赖 ssh 自身 |
| 多个 ssh.exe | 系统自带与 Git 自带不是同一个 | ✅ 已确认两套：System32 9.5p2 与 Git 10.5p1（后者更新）；应用需显式探测选择 |
| **ssh-agent 服务被禁用** | 本机 agent 服务 StartType=Disabled，启用需管理员 | 新发现：提供一次性 UAC 提权启用服务，或用 Git 自带 agent 免提权 fallback |
| 路径格式 | config 里 `~/.ssh/...` 与 `C:\Users\...` 混用（笔记里两种都有） | 统一规范化为绝对路径写入，展示时再美化 |
| 首次连接主机指纹 | `ssh -T` 会交互式询问 yes/no 而卡住 | 加 `-o BatchMode=yes -o StrictHostKeyChecking=accept-new`，或在 UI 里显式确认指纹 |
| Argon2id 参数 | 内存 64 MiB 在低配机器上可能偏慢 | ⏳ 标定程序已就绪，待 MSVC 链接器安装后产出实测档位写入 `vault.json` |
| **MSVC 链接器（新增前置）** | 本机无 `link.exe`，Rust/Tauri 无法构建 | 开发环境需安装 VS Build Tools（VCTools）；终端用户用编译好的安装包不受影响 |

### 6.6 透明性原则

每一个会改动系统状态的操作，界面上都要能展开看到**即将执行的原始命令 / 即将写入的文件 diff**，并保留一份操作历史。理由有两个：用户能核对应用没干别的事；出问题时用户可以把命令复制到终端自己跑一遍排查。

### 6.7 数据存放位置

分两处，职责清晰：

| 位置 | 存什么 | 加密 |
|---|---|---|
| **工作空间**（用户指定，§4.7） | 所有密钥资产与机密：私钥副本、口令、PAT、身份元数据、同步索引 | 全部加密 |
| `%APPDATA%/git-account-manager/` | 非机密的本机状态：工作空间路径、窗口尺寸、语言、最近打开 | 不加密 |

判断标准很简单：**换台电脑还需要的东西放工作空间，只对这台机器有意义的放 APPDATA。** 这样"备份工作空间"就等于备份了全部资产，不存在遗漏。

## 7. 开发路线

加密工作空间的引入改变了里程碑顺序：**vault 是所有数据的容器，必须在任何数据落盘之前建好**，否则后面要做痛苦的数据格式迁移。所以它从"某个功能"变成了 M1。

### 云同步为什么放到 v1.1，但加密方案现在就要定死

同步实现可以延后（你也把它列为"后期计划"），但它的**加密方案必须在 M1 一并定稿**——对象名 HMAC、manifest 结构、子密钥派生标签，全都从主密钥派生。这些如果等到做同步时才定，已经建好的工作空间就会不兼容，用户得重新初始化。

所以 M1 的产出包含完整的密钥派生体系（含同步用的子密钥），只是暂时没有代码去用它。

### 里程碑

| 阶段 | 内容 | 工期 |
|---|---|---|
| **M0 · 技术验证** | 不写 UI，只用 Rust 命令行 demo 打通五个高风险点（见下） | 4 天 |
| **M1 · vault 内核** | 信封加密、Argon2id 参数标定、恢复密钥生成与校验、初始化向导、解锁 / 锁定 / 自动锁定、改密码、轮换恢复密钥 | 1.5 周 |
| **M2 · 只读视图 + 导入入库** | config 解析、密钥扫描、指纹、agent 状态、`ssh -T` 探测、四色状态灯；外部密钥导入（含 `.ppk` 转换、配对校验、原文件处置） | 1.5 周 |
| **M3 · 写操作 + 新建向导** | config 托管区块、备份、原子写入、`ssh -G` 校验、操作历史；密钥生成、公钥复制、四步向导 | 1.5 周 |
| **M4 · agent 与自动解锁** | agent 服务管理、按指纹反查身份、口令自动填入、严格模式（私钥不落盘）、诊断项、错误中文化 | 1 周 |
| **M5 · 仓库与地址识别** | 仓库扫描、身份匹配检查、一键切换 remote 与提交身份；归属标识表与 PAT 自动拉取组织、**地址解析与身份推断**、克隆向导、剪贴板感知；PAT 上传公钥 | 1.5 周 |
| **M6 · 打磨发布** | 本地加密导出 / 导入、首次运行引导、安装包与签名、README | 1 周 |
| **v1.1 · 云同步** | R2 / S3 后端、manifest、冲突处理、换机恢复流程 | 2 周 |

**v1.0 合计约 8 周**，加云同步约 10 周（单人全职）。

其中 M2 结束时（约 3.5 周）就有一个真正可用的东西：能把现有的三个 Host 和散落各处的密钥全部加密收编进工作空间，并给出体检报告——此时还不会修改 `~/.ssh` 的任何内容，零风险。

### M0 要验证的五件事

任何一个走不通都会反过来改设计，所以必须最先做：

1. **`ssh-add` 非交互输入口令**——先试 `SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force`，失败则改用 `portable-pty` 走 ConPTY
2. **私钥能否不落盘直接加载进 agent**——决定 §4.5 严格模式是否成立
3. **`IdentityFile` 指向 `.pub` 是否可行**——同上，需在目标 OpenSSH 版本实测
4. **`icacls` 收紧私钥 ACL**——验证收紧后 OpenSSH 不再报 `UNPROTECTED PRIVATE KEY FILE`
5. **ssh 工具链探测 + Argon2id 参数标定**——确认 git 实际调用哪个 ssh；实测 Argon2id 在本机跑到 500ms 需要什么参数

### 后续版本

macOS / Linux 实现（平台 trait 已预留）、更多对象存储后端（MinIO / OSS / COS）、GitLab / Gitee API 适配、GPG 提交签名管理、按目录自动切换身份（git 的 `includeIf`）。

## 8. 已确认的决策

| 项 | 决定 |
|---|---|
| 技术栈 | Tauri 2 + React + TypeScript / Rust |
| 平台 | 先做 Windows；平台相关操作收在 trait 后面，为 macOS / Linux 预留 |
| 应用形态 | 普通窗口应用，不常驻托盘、不开机自启 |
| 数据权威源 | 加密工作空间；`~/.ssh` 降级为可重建的投放目标 |
| 加密方案 | Argon2id + XChaCha20-Poly1305，主密钥双信封（访问密码 / 恢复密钥） |
| 解锁方式 | 访问密码解锁会话；查看私钥 / 口令明文时二次重输密码。恢复密钥**仅**用于忘记密码和换机恢复，不参与日常操作 |
| 私钥落盘 | 默认方案：每把私钥强制带随机强口令，磁盘副本本身即密文。§4.5 的严格模式暂不做默认，M0 验证通过后作为可选项保留 |
| 云同步 | 端到端加密，用户自带 R2 / S3 存储桶；v1.1 实现，加密方案 M1 定稿 |
| 地址识别 | 以身份的归属标识表（§3.9）为第一优先级，纯本地查表；未登记的 owner 才回退到启发式与实测探测 |
| v1.0 范围 | 身份 + 密钥 + config + agent + vault + 导入 + 仓库管理 + 地址识别 + PAT 上传 |

### PAT 带来的额外要求

用 GitHub API 上传公钥需要 token 具备 `admin:public_key` 权限。由此多出三件必须做的事：

1. Token 存进 vault 加密保管，**绝不落明文**，且日志中一律脱敏
2. Token 是可选项——用户不填也必须能用（回退到"复制公钥 + 打开设置页"的手动方式），不能把 PAT 做成硬依赖
3. 界面上要明示所需权限范围，并提供直达 GitHub token 创建页（已预填 scope）的链接

### 待你确认

- **导入后原文件的默认处置**——默认"保留原文件"最安全，但你笔记里那把散在 `D:\codeProgrammer\...` 的密钥，可能更希望"移入工作空间并擦除原文件"
- **仓库扫描的默认根目录**——暂定 `D:\coding_program`，扫描深度限 5 层，跳过 `node_modules` / `target` / `.venv`
- **已有配置的迁移方式**——首次运行发现现有三个 Host 时，逐个询问还是一次性纳入并展示 diff
