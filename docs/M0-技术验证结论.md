# M0 技术验证结论

> 验证时间：2026-09-08
> 环境：Windows 10.0.26200 (AMD64)、System32 OpenSSH 9.5p2、Git for Windows 自带 OpenSSH 10.5p1
> 目的：在写业务代码前，先打通五个最可能翻车的高风险点

---

## 结论速览

| 编号 | 验证项 | 结论 | 对设计的影响 |
|---|---|---|---|
| M0-1 | `ssh-add` 非交互喂口令 | ✅ 成立 | 用 `SSH_ASKPASS` 即可，**无需 ConPTY** |
| M0-2 | 私钥不落盘直接进 agent | ✅ 成立 | `ssh-add -` 读 stdin，严格模式可行 |
| M0-3 | `IdentityFile` 指向 `.pub` | ✅ 成立 | 私钥可只存在于 agent，磁盘仅留公钥 |
| M0-4 | `icacls` 收紧私钥 ACL | ⚠️ 机制有效，但本机 ssh 不强制 | icacls 作为主动加固保留；不能依赖 ssh 自身拒绝 |

**总体判断：严格模式（私钥全程不落盘）在技术上完全可行，是本项目最重要的一个正向结论。**

## M0-1 · ssh-add 非交互输入口令 ✅

**问题**：Windows 的 `ssh-add` 从控制台读口令，程序无法简单地从 stdin 喂入。

**验证**：设置 `SSH_ASKPASS=<脚本>`、`SSH_ASKPASS_REQUIRE=force`，脚本内容为 `echo "<口令>"`，然后对带口令的密钥执行 `ssh-add <key>`，全程不提供任何控制台输入。

**结果**：
```
Identity added: ...\g_pass (m0-gpass)
```
口令被 askpass 程序非交互地提供，密钥成功加载。

**结论**：`SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force` 方案成立，**不需要退化到 ConPTY 伪终端**。应用只需在解锁 vault 后，用一个从 vault 取口令的 askpass 辅助程序即可自动加载密钥。

---

## M0-2 · 私钥不落盘直接加载进 agent ✅

**问题**：严格模式要求私钥明文不写磁盘，但 agent 通常从文件加载。

**验证**：把内存中的私钥内容通过管道喂给 `ssh-add -`（连字符表示从 stdin 读）。

**结果**：
```
Identity added: (stdin) (m0-free)
256 SHA256:f7Ur0uSM/... m0-free (ED25519)
```
agent 列表里该密钥来源显示为 `(stdin)`，**没有任何文件路径**。

**结论**：私钥可以只存在于内存、经 stdin 加载进 agent，磁盘上无需保留私钥文件。这是严格模式的核心前提，已打通。

---

## M0-3 · IdentityFile 指向 .pub 是否可行 ✅

**问题**：能否让 `~/.ssh/config` 的 `IdentityFile` 指向公钥 `.pub`，由 ssh 去 agent 里找对应私钥签名，从而磁盘只留公钥？

**验证**：config 写 `IdentityFile <key>.pub` + `IdentitiesOnly yes`，私钥已在 agent 中，连 `git@github.com`（`-vv`）。

**结果**（关键日志）：
```
Will attempt key: ...\g_pass.pub ED25519 SHA256:hzXd... explicit agent
Offering public key: ...\g_pass.pub ED25519 SHA256:hzXd... explicit agent
```
ssh 读取 `.pub`、匹配到 **agent 中的私钥**（`explicit agent`）、向服务器提交认证（GitHub 因该测试公钥未注册而拒绝，属预期）。

**结论**：成立。结合 M0-2，严格模式的完整闭环为：
`vault 解密私钥 → ssh-add - (stdin) → agent` + `config 中 IdentityFile 指向 .pub`，
**磁盘上永远只有公钥，私钥明文全程不落盘。**

---

## M0-4 · icacls 收紧私钥 ACL ⚠️

**问题**：私钥文件权限过宽时，OpenSSH 是否拒绝（`UNPROTECTED PRIVATE KEY FILE`）？icacls 能否修复？

**验证**：
1. 对私钥文件 `icacls <key> /grant "*S-1-1-0:R"`（授予 Everyone 读），确认 ACL 变为 `Everyone:(R) + 用户:(F)`。
2. 用 System32 ssh 9.5p2 以该文件连 github（`-vvv`）。
3. `icacls <key> /inheritance:r /grant:r "<用户>:F" /remove:g "*S-1-1-0"` 收紧，确认 ACL 只剩 `用户:(F)`。

**结果**：
- icacls 放宽与收紧命令**均成功执行，ACL 按预期变化**。
- 但即使 ACL 含 `Everyone:(R)`，System32 OpenSSH 9.5p2 **仍照常加载并使用了该私钥，未报任何权限告警**，直接进入 `Offering public key`。

**结论**：
- icacls 作为**主动加固手段有效**，应用应在生成/导入密钥时收紧 ACL。
- 但**不能依赖 OpenSSH 自身拒绝**权限过宽的私钥——至少本机 9.5p2 客户端不强制。笔记中提到的 `UNPROTECTED PRIVATE KEY FILE` 可能出现在其他版本、其他所有者，或经服务态 agent 加载时。
- 好消息：既然默认走 agent 加载（M0-2/M0-3），ssh 根本不会去读磁盘私钥文件，这个权限检查在主路径上不触发，风险进一步降低。

## M0-5 · ssh 工具链探测 + Argon2id 参数标定

### ssh 工具链探测 ✅

| 项 | 结果 |
|---|---|
| System32 OpenSSH | `C:\Windows\System32\OpenSSH\ssh.exe`，版本 **9.5p2** / LibreSSL 3.8.2 |
| Git 自带 OpenSSH | `C:\Program Files\Git\usr\bin\ssh.exe`，版本 **10.5p1** / OpenSSL 3.5.7 |
| ssh-agent 服务 | 状态 **Stopped**、启动类型 **Disabled** |
| 独立运行 System32 ssh-agent | ❌ 失败，报 `error :1058`（服务被禁用），Windows 原生 agent 只能作为服务 |
| 独立运行 Git 自带 ssh-agent | ✅ 成功，可作为普通进程运行并提供 `SSH_AUTH_SOCK` |

**重要结论**（超出原计划，属新发现）：

1. **本机存在两套 OpenSSH，且 Git 自带的（10.5p1）比系统的（9.5p2）更新。** 应用必须显式探测并让用户知道"当前用的是哪个 ssh"，因为 git 默认可能调用其中任意一个，行为（如权限检查、算法支持）会不同。

2. **ssh-agent 服务被禁用（Disabled）。** 按笔记的做法（`Set-Service ssh-agent -StartupType Automatic; Start-Service`）启用它**需要管理员权限**，非提权进程会失败。因此应用需要：
   - 提供一次性的 UAC 提权步骤来启用系统 agent 服务；**或**
   - 用 Git 自带的 ssh-agent 作为**无需管理员的 fallback**（已验证可独立运行）。
   这一条直接影响"agent 管理"模块的实现，应在 M4 落实两条路径。

### Argon2id 参数标定 ✅

安装 VS Build Tools（MSVC 链接器）后，标定程序（`m0-crypto/`）编译运行通过。全套加密原语（argon2 / xchacha20poly1305 / hkdf / sha2 / zeroize）在本机编译、运行、篡改检测均正常。

**本参考机实测（12 逻辑核心）**：

| mem | iters | parallelism | 单次耗时 |
|---|---|---|---|
| 64 MiB | 3 | 4 | 110 ms |
| 128 MiB | 3 | 4 | 252 ms |
| 192 MiB | 3 | 4 | 373 ms |
| **256 MiB** | **3** | **4** | **503 ms** ← 命中目标 |
| 256 MiB | 4 | 4 | 613 ms |
| 384 MiB | 3 | 4 | 779 ms |
| 512 MiB | 3 | 4 | 1043 ms |

**结论**：
- 设计文档原默认 **64MiB/3/4 在这台机器只有 110ms，偏低**（对拥有 GPU/ASIC 的攻击者防护不足）。
- 命中约 500ms 的档位是 **256MiB/3/4**。
- 印证了"必须运行时按机器标定"的设计：不同机器差异巨大，不能写死。策略应为——在内存上限（如 256–512MiB）与时间目标带（如 350–700ms）内自动选参，并设 OWASP 下限（19MiB/2）兜底低配机。

**附带环境结论**：开发/自编译需要 VS Build Tools（MSVC 链接器）；终端用户用编译好的安装包不受影响。加密栈本身在本机零兼容性问题。

## 对设计文档的回填要点

1. §4.5 严格模式：**从"待验证的可选项"升级为"已验证可行"**。默认方案（私钥带口令落盘）与严格方案（私钥仅在 agent）均成立。
2. §3.5 / §6.5 agent 管理：新增"agent 服务被禁用时的两条路径"——UAC 提权启用服务，或用 Git 自带 agent 作免提权 fallback。
3. §6.5 风险表：`ssh-add` 口令输入一项可从"风险"降级——`SSH_ASKPASS` 方案已验证，ConPTY 列为备用。
4. §6.1 工具链：明确记录"存在两套 ssh，Git 自带较新"，应用需显式选择并展示。
5. 新增前置依赖说明：开发环境需 VS Build Tools（MSVC 链接器）。
