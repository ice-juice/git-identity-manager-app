# 程序更新功能设计（GitHub Release 自更新 + 可自定义更新源）

> 配套文档：`开发计划_found.md`（总体开发计划）
> 本文定位：把「基于 GitHub 发布程序更新、允许客户端自定义更新源、默认指向某个 Git 仓库」这项功能，从需求落成**可执行的设计与实现规划**。
> 制定日期：2026-09-09
> 目标里程碑：**M7 · 应用自更新**（在 v1.1 云同步之后）

---

## 第一部分 · 目标与范围

### 1.1 功能目标

| 编号 | 目标 | 说明 |
|---|---|---|
| G1 | GitHub Release 自更新 | 从 GitHub Releases 检查、下载、校验、安装新版本。 |
| G2 | 可自定义更新源 | 用户可把更新源改成任意 GitHub 仓库、任意静态清单 URL，或企业内网镜像。 |
| G3 | 默认更新源 | 出厂内置一个默认 GitHub 仓库地址，开箱即用、无需配置。 |
| G4 | 安全校验 | 更新包必须经过签名校验（minisign），防止中间人替换安装包。 |
| G5 | 良好体验 | 支持启动时静默检查、手动检查、更新日志展示、后台下载、一键安装重启。 |
| G6 | **全平台交付** | **本期一次性覆盖 Windows（NSIS `.exe` + MSI）、macOS Universal（Intel + Apple Silicon 单包）、Linux（AppImage）。** |

### 1.2 非目标（本期不做）

- 增量/差分更新（delta patch）——首版走整包替换。
- 强制更新 / 灰度分发比例控制——预留 `channel` 字段，逻辑后置。
- 应用商店（Microsoft Store / Mac App Store）渠道——与自更新互斥，不在本期。
- Linux 的 `.deb` / `.rpm` 自更新——包管理器管控的格式不走应用内更新，仅提供 AppImage 自更新（其余格式给「手动下载」链接兜底）。

## 第二部分 · 技术选型

### 2.1 核心：`tauri-plugin-updater`

复用 Tauri 官方更新插件，而非手写下载器。理由：

- 原生支持**全平台安装 + 自动重启**（Windows NSIS/MSI 静默安装、macOS `.app` 原地替换、Linux AppImage 自替换），这部分手写极易出错。
- 内置 **minisign 签名校验**，与 `tauri` 打包签名链路打通。
- 支持**运行时动态设置 endpoints**（`UpdaterBuilder::endpoints`），正好满足「自定义更新源」。
- 与现有 `reqwest`（rustls-tls）栈兼容，无需额外网络层。

需要新增依赖：

```toml
# app/src-tauri/Cargo.toml
[dependencies]
tauri-plugin-updater = "2"
```

```jsonc
// app/package.json
"@tauri-apps/plugin-updater": "^2",
"@tauri-apps/plugin-process": "^2"  // 安装后重启应用
```

### 2.2 为什么不直接用插件内置的 GitHub endpoint

插件的 endpoints 是**编译期**写死在 `tauri.conf.json` 里的。而 G2 要求**运行时**可改更新源，所以采用：

> **薄命令层在 Rust 端读取用户配置 → 动态构造 `UpdaterBuilder` 的 endpoints → 再调用插件完成 check/download/install。**

这样既拿到插件的安装/校验能力，又保留了自定义源的灵活性。

## 第三部分 · 更新源模型

### 3.1 两种源类型

```
UpdateSourceKind
├── github     从 GitHub Releases 取更新（默认）
└── manifest   直接给一个静态清单 URL（内网镜像 / 自建 CDN / 其它 Git 平台 raw）
```

#### github 模式

给定 `owner/repo`，解析为 GitHub「最新 Release」资产里的清单地址：

```
https://github.com/{owner}/{repo}/releases/latest/download/latest.json
```

- 该 URL 由 GitHub 自动指向最新正式 Release，无需调用有速率限制的 API。
- 如需支持 pre-release / 指定 tag，再走 GitHub API：`GET /repos/{owner}/{repo}/releases`。

#### manifest 模式

用户直接填一个清单 URL（支持 `{{target}}`、`{{arch}}`、`{{current_version}}` 占位符），例如：

```
https://mirror.example.com/gam/latest.json
https://gitee.com/{owner}/{repo}/raw/release/latest.json
```

### 3.2 更新清单格式（`latest.json`）

沿用 Tauri updater 的标准「静态 JSON」格式，随每次 Release 作为资产上传：

```json
{
  "version": "1.2.0",
  "notes": "本次更新说明（支持多行 / Markdown）",
  "pub_date": "2026-09-09T12:00:00Z",
  "platforms": {
    "windows-x86_64": {
      "signature": "<minisign 签名内容>",
      "url": "https://github.com/{owner}/{repo}/releases/download/v1.2.0/Git.Keymaster_1.2.0_x64_zh-CN-setup.exe"
    },
    "darwin-x86_64": {
      "signature": "<minisign 签名内容>",
      "url": "https://github.com/{owner}/{repo}/releases/download/v1.2.0/Git.Keymaster_1.2.0_universal_zh-CN.app.tar.gz"
    },
    "darwin-aarch64": {
      "signature": "<minisign 签名内容>",
      "url": "https://github.com/{owner}/{repo}/releases/download/v1.2.0/Git.Keymaster_1.2.0_universal_zh-CN.app.tar.gz"
    },
    "darwin-universal": {
      "signature": "<minisign 签名内容>",
      "url": "https://github.com/{owner}/{repo}/releases/download/v1.2.0/Git.Keymaster_1.2.0_universal_zh-CN.app.tar.gz"
    },
    "linux-x86_64": {
      "signature": "<minisign 签名内容>",
      "url": "https://github.com/{owner}/{repo}/releases/download/v1.2.0/Git.Keymaster_1.2.0_amd64_zh-CN.AppImage"
    }
  }
}
```

- `platforms` 的 key 为 `{target}-{arch}`。本期覆盖：`windows-x86_64`、`linux-x86_64`，以及 macOS 的 `darwin-x86_64` / `darwin-aarch64` / `darwin-universal`（后三者指向**同一份 Universal `.app.tar.gz`**，由 `tauri-action` 的 `updaterJsonKeepUniversal` 写入）。
- 各平台 `url` 指向对应的更新产物：Windows → NSIS `.exe`；macOS → Universal `.app.tar.gz`；Linux → `.AppImage`。`signature` 为对应 `.sig` 文件内容。
- 插件按当前运行环境的 `{target}-{arch}` 自动选择对应条目；若清单缺失当前平台条目，则视为「无可用更新」并回落到「手动下载」。
- 版本比较用语义化版本（semver），`version` 必须与 `tauri.conf.json` 的 `version` 一致。

## 第四部分 · 配置与数据结构

### 4.1 后端配置（追加到 `AppConfig`）

更新源属于「本机偏好」，放 `%APPDATA%\git-keymaster\config.json`（`app_config.rs`），不进加密工作空间。

```rust
// app_config.rs
/// 内置默认更新源仓库（出厂值，用户可覆盖）。
pub const DEFAULT_UPDATE_REPO: &str = "ice-juice/git-keymaster-app";

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct UpdateSource {
    /// "github" | "manifest"
    pub kind: String,
    /// github 模式：owner/repo；manifest 模式留空。
    pub repo: Option<String>,
    /// manifest 模式：清单 URL；github 模式留空。
    pub manifest_url: Option<String>,
    /// 是否接受 pre-release（github 模式）。
    #[serde(default)]
    pub include_prerelease: bool,
}

// AppConfig 内新增字段：
/// 更新源（None 表示使用内置默认 GitHub 仓库）。
#[serde(default)]
pub update_source: Option<UpdateSource>,
/// 启动后自动检查更新（默认开启）。
#[serde(default = "default_true")]
pub auto_check_update: bool,
/// 用户「跳过」的版本号，避免重复打扰。
#[serde(default)]
pub skipped_update_version: Option<String>,
/// 最近一次检查时间（ISO）。
#[serde(default)]
pub last_update_check_at: Option<String>,
```

> 旧配置无这些字段时靠 `#[serde(default)]` 平滑升级——与现有 `cloud_sync`、`close_action` 的兼容做法一致。

### 4.2 前端类型（`ipc.ts`）

```ts
export interface UpdateSource {
  kind: "github" | "manifest";
  repo?: string;
  manifestUrl?: string;
  includePrerelease: boolean;
}

export interface UpdateCheckResult {
  available: boolean;
  currentVersion: string;
  latestVersion: string | null;
  notes: string | null;
  pubDate: string | null;
  source: UpdateSource;           // 实际使用的源（含默认回填）
  downloadUrl: string | null;     // 供「手动下载」兜底
  platform: string;              // 当前运行平台键，如 "windows-x86_64"
  selfUpdateSupported: boolean;  // false 时（如非 AppImage 的 Linux）仅提供手动下载
}

export interface UpdateProgress {
  phase: "started" | "downloading" | "finished";
  downloaded: number;
  total: number | null;
}
```

### 5.1 目录结构（新增 `update/` 模块，风格对齐 `sync/`）

```

├── update/
│   ├── mod.rs          模块导出 + UpdateSource 相关 helper

│   └── scheduler.rs    启动/定时静默检查（复用 sync/scheduler 的线程范式）
└── commands/
    └── update.rs       IPC 命令层（薄封装）
```

### 5.2 源解析（`update/source.rs`）

```rust
/// 把用户配置（或默认值）解析为插件可用的 endpoints。
pub fn resolve_endpoints(src: &UpdateSource) -> Result<Vec<Url>> {
    match src.kind.as_str() {
        "github" => {
            let repo = src.repo.clone()
                .unwrap_or_else(|| DEFAULT_UPDATE_REPO.to_string());
            // 校验 owner/repo 形态，拒绝奇怪输入
            let url = format!(
                "https://github.com/{repo}/releases/latest/download/latest.json"
            );
            Ok(vec![Url::parse(&url)?])
        }
        "manifest" => {
            let raw = src.manifest_url.as_deref()
                .ok_or_else(|| AppError::Invalid("未填写清单 URL".into()))?;
            Ok(vec![Url::parse(raw)?])
        }
        other => Err(AppError::Invalid(format!("未知更新源类型：{other}"))),
    }
}

/// 返回「有效源」——None 配置回填为默认 GitHub 仓库。
pub fn effective_source(cfg: &AppConfig) -> UpdateSource { /* ... */ }
```

### 5.3 IPC 命令（`commands/update.rs`）

| 命令 | 签名 | 作用 |
|---|---|---|
| `get_update_source` | `() -> UpdateSource` | 读取有效更新源（回填默认）。 |
| `save_update_source` | `(source: Option<UpdateSource>) -> ()` | 保存/重置更新源；`None` 恢复默认。 |
| `set_auto_check_update` | `(enabled: bool) -> ()` | 开关启动自动检查。 |
| `check_update` | `() -> UpdateCheckResult` | 立即检查，返回是否有新版本 + 说明。 |
| `download_and_install_update` | `() -> ()` | 下载→校验→安装，进度经事件回传，完成后重启。 |
| `skip_update_version` | `(version: String) -> ()` | 记住「跳过此版本」。 |
| `get_last_update_check` | `() -> Option<String>` | 最近检查时间。 |

关键实现骨架（动态 endpoints 是核心）：

```rust
#[tauri::command]
pub async fn check_update(app: AppHandle, state: State<'_, AppState>) -> Result<UpdateCheckResult> {
    let src = update::source::effective_source(&state.config.lock().unwrap());
    let endpoints = update::source::resolve_endpoints(&src)?;

    let updater = app.updater_builder()
        .endpoints(endpoints)?          // ← 运行时注入自定义源
        .build()?;

    match updater.check().await? {
        Some(update) => Ok(UpdateCheckResult {
            available: true,
            current_version: app.package_info().version.to_string(),
            latest_version: Some(update.version.clone()),
            notes: update.body.clone(),
            /* ... */
        }),
        None => Ok(/* available: false ... */),
    }
}
```

下载安装（进度事件对齐现有 `cloud-auto-sync` 事件命名习惯，用 `update-progress`）：

```rust
#[tauri::command]
pub async fn download_and_install_update(app: AppHandle, state: State<'_, AppState>) -> Result<()> {
    // ...构造 updater 同上...
    if let Some(update) = updater.check().await? {
        let mut downloaded = 0u64;
        update.download_and_install(
            |chunk, total| {
                downloaded += chunk as u64;
                let _ = app.emit("update-progress", json!({
                    "phase": "downloading", "downloaded": downloaded, "total": total
                }));
            },
            || { let _ = app.emit("update-progress", json!({ "phase": "finished" })); },
        ).await?;
        app.restart(); // tauri-plugin-process
    }
    Ok(())
}
```

### 5.4 启动自动检查（`update/scheduler.rs`）

- 复用 `sync/scheduler.rs` 的**独立后台线程**范式，进程启动后延迟 ~5s 触发一次静默检查（错开云同步的启动拉取，避免抢网络）。
- 命中新版本且未被 `skipped_update_version` 跳过时，`emit("update-available", result)`，前端在角落弹出非阻断提示。
- 失败静默记录，不打扰用户（更新检查失败不影响核心功能）。
- 只在**已解锁**且窗口存在时提示，避免锁屏界面弹更新。

### 5.5 注册（`lib.rs`）

### 6.2 设置页「关于与更新」区块（`pages/Settings.tsx`）

- **当前版本**：显示 `1.1.0` 与最近检查时间。
- **立即检查更新**按钮：调用 `checkUpdate`，展示结果。
- **更新源设置**：
  - 单选：`GitHub 仓库` / `自定义清单 URL`。
  - GitHub 模式：`owner/repo` 输入框（占位显示内置默认值），`包含预发布版本`开关。
  - 清单模式：URL 输入框。
  - `恢复默认`按钮 → `saveUpdateSource(null)`。
- **自动检查更新**开关。
- 发现新版本时展示：版本号、发布时间、更新日志（`notes`），按钮：`下载并安装` / `跳过此版本` / `手动下载`（打开 `downloadUrl`）。
- **平台适配**：当 `selfUpdateSupported === false`（如 `.deb`/`.rpm` 安装的 Linux 实例）时，隐藏「下载并安装」，只保留「手动下载」并提示用户按安装渠道更新。

部分地区直连 GitHub 失败时，检查/下载须走用户配置的代理，设计见 [`网络代理设置设计.md`](./网络代理设置设计.md)。

### 6.3 全局更新提示

- 监听 `update-available` 事件（`App.tsx` 或 `Layout.tsx`），在右下角显示轻量 Toast/角标：「发现新版本 v1.2.0」。

## 第七部分 · 打包与发布链路（CI / 本地）

> 这是让自更新真正跑起来的前提，必须与代码同步落地。
> **发布依据：只认 `release` 分支。** `main` 用于日常开发；要出包或发版，先把稳定提交合入 / 快进到 `release`，再在该分支上构建或打 `v*` 标签。

### 7.0 分支与触发约定

| 动作 | 结果 |
|---|---|
| 把代码推到 `dev` 或 `release` | 跑 `.github/workflows/ci.yml` 的三平台 `cargo test`，**不打包** |
| 只把代码推到 `release`（不打标签） | **不打包**（避免和打标签各跑一轮三平台构建） |
| 在 `release` 上打并推送 `v*` 标签 | 先 2 路 Unix `cargo test`（preflight），通过后再构建 + 创建**草稿** Release + 合并生成 `latest.json` |
| Actions → `Release packages` → Run workflow | 可选抽检出包；勾选 `create_release` 时建草稿 Release（须在 `release` 上触发） |
| 在 `main` 或其它分支打 `v*` 标签 | workflow **拒绝**（标签必须是 `release` 的祖先提交） |

工作流文件：`.github/workflows/ci.yml`（推分支只测）、`.github/workflows/release.yml`（打标签才出包）。

### 7.1 生成更新签名密钥（一次性）

```powershell
npm run tauri signer generate -- -w %USERPROFILE%\.tauri\gam-updater.key
```

- 生成私钥 `gam-updater.key`（**绝不入库**，作为 CI Secret：`TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`）。
- 公钥填入 `tauri.conf.json` 的 `plugins.updater.pubkey`。

> 该密钥**全平台共用同一把**——Windows/macOS/Linux 的更新产物都用它签名，前端内置的公钥统一校验。

### 7.2 `tauri.conf.json` 增量

```jsonc
{
  "bundle": {
    // 已有 "targets": "all"；确认各平台产出更新可用格式：
    // windows → nsis；macOS → app；linux → appimage
    "createUpdaterArtifacts": true   // v2 需显式开启，才会生成 .sig 与更新用产物
  },
  "plugins": {
    "updater": {
      "pubkey": "<上一步生成的公钥，当前 tauri.conf.json 留空占位>",
      "endpoints": [
        "https://github.com/ice-juice/git-keymaster-app/releases/latest/download/latest.json"
      ]
    }
  }
}
```

> 说明：这里的 `endpoints` 仅作为**编译期默认兜底**；运行时会被命令层按用户配置覆盖。`pubkey` 是签名校验根，必须内置。`createUpdaterArtifacts` 开启后，Windows 产 NSIS `.exe` + `.sig`、macOS 产 `.app.tar.gz` + `.sig`、Linux 产 `.AppImage` + `.sig`。

"permissions": [

### 7.4 各平台发布产物

`tauri build` 在 **GitHub Actions 矩阵**的各自平台上构建（更新产物必须在目标平台或对应交叉环境产出）。macOS **采用 Universal 单包**（`--target universal-apple-darwin`），不再分架构双包。

| 平台 | 构建环境 | 更新产物 | 签名 |
|---|---|---|---|
| Windows x64 | `windows-latest` | `Git.Keymaster_1.2.0_x64_zh-CN-setup.exe` / `*_en-US-setup.exe` | `.exe.sig` |
| macOS Universal | `macos-latest` | `Git.Keymaster_1.2.0_universal_zh-CN.app.tar.gz` / `*_en-US.app.tar.gz` | `.tar.gz.sig` |
| Linux x64 | `ubuntu-22.04` | `Git.Keymaster_1.2.0_amd64_zh-CN.AppImage` / `*_en-US.AppImage` | `.AppImage.sig` |

> Linux AppImage 在 `ubuntu-22.04`（较老 glibc）上构建以保证兼容性。Windows 出 NSIS + MSI（`updaterJsonPreferNsis`）。安装包文件名统一为 `Git.Keymaster_{version}_{arch}_{zh-CN|en-US}`，界面标题仍按语言显示「御钥师」或 Git Keymaster。

**日常发版请按操作手册走，不要只记下面这四句：** [`docs/发布新版本流程.md`](./发布新版本流程.md)

摘要（已落入 `.github/workflows/release.yml`）：

1. 先在仓库里手改版本号（Actions 不会自动升版本），在本地把提交合入 `release` 并打上 `vX.Y.Z`，再**先推分支、后推标签**（只推分支不打包）。
2. 推送 `vX.Y.Z` → 先跑 Unix `cargo test`，通过后各 runner 把产物与 `.sig` 挂到**同一份草稿 Release**。用 `gh run watch` 盯包：preflight 红了立刻停，6 路打包全绿再 Publish；失败则按日志修完再出包。
3. `tauri-action`（`includeUpdaterJson: true` + `updaterJsonKeepUniversal: true`）合并生成 `latest.json`，作为 Release 资产上传。
4. 在 GitHub 上检查草稿无误后点 Publish（不要标 Pre-release）；`releases/latest/download/latest.json` 即指向它。旧安装版才能检测到应用内更新。

发版前须在仓库 **Settings → Secrets and variables → Actions** 配置：

- `TAURI_SIGNING_PRIVATE_KEY`
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`

未配置时，因 `createUpdaterArtifacts: true`，CI 构建会失败。公钥填入 `tauri.conf.json` 的 `plugins.updater.pubkey`（当前为空字符串占位）。

### 7.5 平台特有注意事项

- **macOS 签名/公证**：自更新的 minisign 签名与 Apple 代码签名/公证是**两回事**。未做 Apple 公证时，`.app` 首次打开会被 Gatekeeper 拦截；正式分发建议补齐 Apple Developer 签名 + notarization（可作为 T8 的可选增强，不阻塞自更新闭环）。
- **Linux AppImage**：自更新要求应用**以 AppImage 形态运行**（依赖 `APPIMAGE` 环境变量定位自身）。通过 `.deb`/`.rpm` 安装的实例不支持应用内自更新，前端应检测并只显示「手动下载」。
- **Windows**：NSIS + MSI，中英文文件名用 `zh-CN` / `en-US` 成对区分。

### 7.6 升级说明（CHANGELOG → `latest.json.notes`）

客户端已经把 updater 的 `body` 映射为 `UpdateCheckResult.notes`，并在设置页展示。缺的是发版时把说明写进 Release body——`tauri-action` 的 `uploadVersionJSON(version, notes, …)` 用的就是这份 body。

**数据源：** `CHANGELOG.md` 只写三份清单；`docs/release-download-guide.md` 只写「下载建议」。应用内更新说明和 tag Release notes 都只展示这四份清单。不要一版一个散文件，也不要用 `generateReleaseNotes`。

章节标题必须能被 CI 按 tag 抽取：

```markdown
## [1.2.0] - 2026-09-10

### 新增功能
- **身份管理**：支持从已有 SSH 配置一键导入身份

### 优化功能
- **设置页**：关于与更新区展示最近检查时间

### 修复问题
- **身份切换**：修复 Windows 下切换后 `git user.name` 未即时生效
```

写作约定：面向用户；`- **模块**：动作`；一屏大约 8–15 条。不要写导语、设计说明或 commit 记录。

**CI（已落入 `release.yml` + `scripts/build-release-notes.sh`）：**

1. 仅当 `refs/tags/v*` 时执行 `Load release notes`。
2. 脚本只保留 `### 新增功能` / `### 优化功能` / `### 修复问题` 及其条目（兼容旧标题「新增 / 优化 / 修复」并改成全称）。
3. 其它标题、段落、`[Unreleased]`、文首说明一律丢弃。
4. 再追加 `docs/release-download-guide.md` 里的 `### 下载建议` 清单（`{{VERSION}}` 会替换成当前版本号）。
5. 抽不到任何功能清单或缺少下载建议 → 构建失败。
6. 各矩阵 runner 生成同一份 notes，传给 `tauri-action` 的 `releaseBody`。
7. 手动 Run workflow 抽检（tag 为占位 `v__VERSION__`）跳过本步，`releaseBody` 为空。

**不要做：**

- 草稿生成后再只在 GitHub 网页改 Release 描述——`latest.json` 不会跟着变，客户端仍读旧 `notes`。要改就改 `CHANGELOG.md` 或下载建议文件后重打/重跑。
- 把长篇开发笔记或额外章节塞进 notes；细节留在 commit / PR / 设计文档。

升级后欢迎页（安装前把 `notes` 写入 `config.json`，重启弹一次）为后置增强，不阻塞本条。操作步骤见 [`发布新版本流程.md`](./发布新版本流程.md)。
部分地区直连 GitHub 失败时，检查/下载须走用户配置的代理，见 [`网络代理设置设计.md`](./网络代理设置设计.md)。

## 第八部分 · 安全与健壮性

| 关注点 | 措施 |
|---|---|
| 安装包被篡改 | minisign 签名校验（插件强制），公钥内置于二进制。 |
| 自定义源风险 | 无论何种源，**签名校验不可跳过**；私钥不在源侧，换源也无法伪造合法包。 |
| 仅 HTTPS | 校验 endpoints 必须为 `https://`（manifest 模式尤其），拒绝明文。 |
| 输入校验 | `owner/repo` 正则校验；URL 解析失败给出明确错误。 |
| 降级版本 | 语义化版本比较，禁止「更新」到更低版本。 |
| 网络失败 | 检查/下载失败不影响主功能，静默记录 + 手动重试；提供「手动下载」兜底。 |
| 打扰控制 | `skipped_update_version` + 每次启动只提示一次。 |
| 与云同步共存 | 启动检查错开云同步拉取时序，避免同时抢占网络与 UI。 |

## 第九部分 · 任务拆解与验收

| 序 | 任务 | 交付物 | 验收标准 |
|---|---|---|---|
| T1 | 引入依赖与插件注册 | `Cargo.toml`/`package.json`/`lib.rs` | `cargo build` 通过，插件加载无 panic。 |
| T2 | 配置结构与迁移 | `app_config.rs` 新字段 + 测试 | 旧 `config.json` 可无损加载，默认源回填正确。 |
| T3 | 源解析模块 | `update/source.rs` + 单测 | github/manifest 两模式解析正确，非法输入报错。 |
| T4 | IPC 命令层 | `commands/update.rs` | 七个命令可被前端调用，check 能返回真实结果。 |
| T5 | 启动自动检查 | `update/scheduler.rs` | 启动后静默检查，命中发 `update-available`。 |
| T6 | 前端设置区块 | `Settings.tsx` + `ipc.ts` | 可切换源、检查、下载安装、跳过、恢复默认。 |
| T7 | 全局提示与进度 | `App/Layout` 事件监听 | Toast 提示 + 进度条正确显示。 |
| T8 | 签名与多平台发布链路 | 密钥、`tauri.conf.json`（`createUpdaterArtifacts`）、以 `release` 分支为依据的 GitHub Actions 矩阵、合并版 `latest.json` | Windows / macOS Universal / Linux 产物 + `.sig` 齐备，`latest.json` 含 win / linux / darwin 各条目。 |
| T9 | 平台运行环境适配 | 前端「更新不支持」检测（如 Linux 非 AppImage）、平台键匹配 | 非 AppImage 的 Linux 实例只显示手动下载；各平台正确匹配自己的更新条目。 |
| T10 | 全平台端到端验收 | 三平台各一次真实版本升级 | 各平台默认源与自定义源均跑通，签名被篡改时安装被拒。 |
| C1 | 仓库根 `CHANGELOG.md` | 当前版本与历史版本章节 | 标题为 `## [X.Y.Z]`，可被 CI 抽取 |
| C2 | `release.yml` 注入 `releaseBody` | `build-release-notes.sh` + `releaseBody` | 打 `v*` 后草稿 body 与 `latest.json.notes` 只有四份清单；缺清单则失败 |
| C3 | 发版手册补 CHANGELOG 步骤 | `发布新版本流程.md` | 升版本必写章节；禁止只在网页改说明 |

**里程碑验收（M7 通过标准）**：在干净的 **Windows、macOS（Intel 或 Apple Silicon）、Linux（AppImage）** 各一台机器上安装 vX，服务端发布 vX+1；每个平台都能自动/手动检查到更新、展示更新日志、下载并通过签名校验后安装并重启到新版本；将更新源改为自定义清单 URL 后各平台同样跑通；篡改安装包后安装被拒绝。macOS 若未做 Apple 公证，至少验证 minisign 校验与原地替换流程成功。

## 附录 A · 关键决策记录

- **用官方插件而非手写下载器**：换来安装/重启/签名校验的稳健性，代价是引入两个依赖。
- **运行时动态 endpoints**：为满足「自定义源」，命令层每次 check/install 都按当前配置重建 `UpdaterBuilder`。
- **默认源用 `releases/latest/download`**：避开 GitHub API 速率限制，无需 token。
- **签名根内置、不可关**：这是「允许任意自定义源」的安全前提——源可换，信任根不可换。
- **全平台一次到位、单一 minisign 密钥**：Windows/macOS/Linux 共用一把更新签名密钥、一份 `latest.json`（多 `platforms` 条目），靠矩阵 CI 分平台产出并合并清单。
- **macOS 出 Universal 单包**：`--target universal-apple-darwin`，`latest.json` 的 `darwin-x86_64` / `darwin-aarch64` / `darwin-universal` 指向同一份 `.app.tar.gz`。
- **打包与发版只认 `release` 分支**：`main` 不直接出包；`v*` 标签必须落在 `release` 上。
- **Linux 只自更新 AppImage**：`.deb`/`.rpm` 交给系统包管理器，应用内仅检测并引导手动更新，避免与系统包状态冲突。
- **升级说明只认四份清单**：CI 从 CHANGELOG 抽新增功能 / 优化功能 / 修复问题，再拼下载建议；网页改 Release 描述不会更新客户端看到的说明。
