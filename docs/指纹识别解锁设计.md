# 指纹 / 生物识别解锁设计（v1）

> 配套文档：`规划设计.md`（保险库总体架构与信封模型）、`密码与2FA管理设计.md`（TOTP / 账密查看路径）、`环境安全检测设计.md`（`ensure_reveal_authorized` 免密查看门禁）
> 本文定位：在**不削弱现有密码 / 恢复密钥底座**的前提下，用**平台原生硬件安全能力**为「解锁工作空间」与「查看一次性验证码 / 私密账户」两处操作增加指纹（及人脸 / PIN）解锁。
> 技术路线：**选项 2 —— 平台原生 API，做真安全**（硬件密钥绑定，而非仅"存在性确认"）。
> 制定日期：2026-09-10
> 状态：**设计稿，待评审后分期实施**。

## 第一部分 · 目标与非目标

### 1.1 功能目标

1. **设置界面可自定义开关**：用户可在「安全」设置中开启 / 关闭"指纹解锁"。默认关闭。
2. **指纹解锁可替代密码解锁**：一旦开启并在本机成功登记，解锁工作空间时首选指纹；**验证通过即免输访问密码**。密码解锁与恢复密钥始终保留为回落入口。
3. **隐私操作支持指纹**：查看一次性验证码（TOTP）、查看私密账户密码等敏感操作，在开启后同样可用指纹完成重认证，替代当前的"输入访问密码"。
4. **三平台原生实现**：Windows / macOS 走硬件级真安全；Linux 如实降级为便利级并在 UI 明示。

### 1.2 非目标

- **不替换密码 / 恢复密钥体系**：指纹是"本机便捷入口"，不是唯一凭据。换机、系统重装、清除指纹后必须能用密码 / 恢复密钥找回，杜绝永久锁死。
- **不做跨机同步**：指纹信封绑定本机硬件，绝不写入会同步到云端的 `vault.json`。
- **不改变底层加密算法**：主密钥 MK、Argon2id、XChaCha20-Poly1305 全部沿用。

## 第二部分 · 与现有架构的契合点

现有解锁模型是**信封加密**（见 `app/src-tauri/src/vault/`）：一把随机主密钥 `MasterKey (MK)` 解密所有数据，MK 被两个信封各自包裹并存于 `vault.json`：

```39:52:app/src-tauri/src/vault/header.rs
/// 一个信封：用某来源派生的 KEK 包裹主密钥 MK 的结果（全部 base64）。
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Envelope {
    pub salt: String,
    pub nonce: String,
    #[serde(rename = "wrappedKey")]
    pub wrapped_key: String,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Envelopes {
    pub password: Envelope,
    pub recovery: Envelope,
}
```

并且已经存在**本机限时免验证会话**（`app/src-tauri/src/session.rs`）：用 Windows DPAPI 把 MK 包起来放到 `grace.dpapi`，开机静默还原，入口是 `Vault::unlock_with_master_key`：

```149:158:app/src-tauri/src/vault/mod.rs
    /// 用已恢复的主密钥解锁（仅供本机 DPAPI 免验证会话）。
    pub fn unlock_with_master_key(&mut self, mk: MasterKey) -> Result<()> {
        self.mk = Some(mk);
        let data_file = self.root.join("data").join("identities.enc");
        if data_file.is_file() && crate::store::load_data(self).is_err() {
            self.lock();
            return Err(AppError::BadPassword);
        }
        Ok(())
    }
```

**结论：指纹解锁 = 在这套机制上新增"第三个信封"。** 与 `grace.dpapi`（无条件还原 MK）不同，指纹信封要求"必须先完成生物识别手势，才能派生出解开信封的 KEK"。复用 `unlock_with_master_key` 作为落点，改动面小、风格一致。

## 第三部分 · 威胁模型与两条路线的取舍

必须先分清两个安全等级，否则会做成"假安全"：

| 路线 | 做法 | 抵御能力 |
|---|---|---|
| **A. 存在性确认（consent-only）** | 只问系统"是不是你本人？"通过后就还原早已可解的 MK | 只挡"别人拿到你已登录的电脑随手点开"；密文本身未被指纹保护，拿到文件 + 会话可能绕过 |
| **B. 硬件密钥绑定（key-wrapped）** | 用**存于 TPM / Secure Enclave、且使用时强制刷指纹**的密钥派生 KEK 来包裹 MK | 没有指纹手势，信封密文无法解开；即使文件被拷走也无用 |

**本设计的分工（关键决策）：**

- **解锁工作空间**：MK 尚未在内存中，必须从信封解出 → **走路线 B**（真硬件绑定）。这是安全的核心。
- **隐私操作重认证（查看 OTP / 私密账户）**：此时 vault **已解锁、MK 已在内存**，`ensure_reveal_authorized` 的本质是"再确认一次操作者是本人"的**闸门**，并不需要重新解出 MK → **走路线 A 即可**（存在性确认），成本更低、体验更顺。

> 这个区分很重要：解锁必须硬绑定，重认证只需存在性确认。两者都由平台原生 API 提供，但调用的 API 层次不同。

## 第四部分 · 第三信封：数据结构与存储

### 4.1 存储位置：本机，绝不上云

指纹信封绑定本机硬件，**不放进 `vault.json`**（那是会云同步的），而是与 `grace.dpapi` 并列存于本机配置目录：

```
%APPDATA%/git-keymaster/      (Windows；mac/Linux 见 config_dir())
├── config.json
├── grace.dpapi          # 既有：DPAPI 免验证会话
└── biometric.env        # 新增：指纹信封（本机、按工作空间绑定）
```

### 4.2 `biometric.env` 内容（JSON）

```jsonc
{
  "version": 1,
  "platform": "windows | macos | linux",
  "workspaceId": "<绑定的工作空间 UUID，防串号>",
  "keyRef": "<平台密钥句柄：Win=KeyCredential 名称 / mac=keychain account / linux=secret label>",
  "challenge": "<base64：用于让硬件密钥产生稳定输出的固定随机 challenge，仅 Win/mac 需要>",
  "envelope": {                    // 复用现有 Envelope 结构
    "salt":  "<base64>",
    "nonce": "<base64>",
    "wrappedKey": "<base64：被生物识别 KEK 包裹的 MK>"
  },
  "createdAt": "<ISO8601>"
}
```

- `workspaceId` 与当前 vault 头部的 `workspace_id` 比对，不一致即作废（换工作空间 / 换机残留保护），与 `session.rs` 的做法一致。
- `challenge` 是登记时生成的随机数：每次解锁让硬件密钥对同一个 challenge 产生**确定性输出**（签名 / 派生），再经 HKDF 得到稳定 KEK。

### 4.3 KEK 派生（路线 B 的核心）

登记（enable）时：

1. 生成随机 `challenge`。
2. 调用平台后端，用**受生物识别保护的硬件密钥**对 `challenge` 产生确定性输出 `raw`。
3. `KEK = HKDF-SHA256(ikm = raw, salt = envelope.salt, info = "gam-biometric-kek-v1")`。
4. 用 KEK 通过现有 `aead_encrypt` 包裹 MK，得到 `envelope`，落盘 `biometric.env`。

解锁（unlock）时：重放步骤 2–3 得到同一 KEK（其间系统弹出指纹提示），`aead_decrypt` 解出 MK → `unlock_with_master_key(MK)`。

> 为什么用 HKDF 而非直接拿 `raw` 当 KEK：与现有 `envelope.rs` 里恢复密钥的处理（`recovery_kek`）保持同构，且对不同硬件输出长度做归一化。

## 第五部分 · 三平台原生后端设计

新增模块 `app/src-tauri/src/biometric/`，对上层暴露统一 trait，内部按 `#[cfg]` 分平台（与 `session.rs`、`Cargo.toml` 现有分平台写法一致）：

```rust
// app/src-tauri/src/biometric/mod.rs（示意）
pub struct BiometricAvailability {
    pub available: bool,      // 硬件存在且已登记指纹/人脸/PIN
    pub kind: &'static str,   // "windows-hello" | "touch-id" | "polkit" ...
    pub strong: bool,         // true = 路线 B 可用；false = 仅路线 A（Linux）
}

pub trait BiometricBackend {
    fn availability() -> BiometricAvailability;
    /// 登记：创建/获取硬件密钥，对 challenge 产生确定性输出（路线 B）。
    fn enroll(key_ref: &str, challenge: &[u8]) -> Result<Vec<u8>>;
    /// 解锁：弹出生物识别，复现确定性输出（路线 B）。
    fn derive(key_ref: &str, challenge: &[u8]) -> Result<Vec<u8>>;
    /// 存在性确认：仅确认本人在场，用于隐私操作重认证（路线 A）。
    fn verify_presence(prompt: &str) -> Result<()>;
    /// 注销：删除硬件密钥。
    fn remove(key_ref: &str) -> Result<()>;
}
```

### 5.1 🪟 Windows —— Windows Hello + TPM（路线 B）

- **路线 B（解锁）**：`Windows.Security.Credentials.KeyCredentialManager`
  - `RequestCreateAsync(name, ReplaceExisting)` 创建绑定 TPM、使用时强制 Hello 手势的密钥对（enroll）。
  - `OpenAsync(name)` + `KeyCredential.RequestSignAsync(challenge)` 对固定 challenge 签名；RSA PKCS#1 v1.5 为**确定性签名**，同一密钥 + 同一 challenge 输出稳定 → 可作 HKDF 输入。
  - `keyRef` = 我们自定义的密钥名（含 `workspaceId`，如 `gam-vault-<workspaceId>`）。
- **路线 A（隐私操作重认证）**：`Windows.Security.Credentials.UI.UserConsentVerifier`
  - `CheckAvailabilityAsync` 判可用；`RequestVerificationForWindowAsync(hwnd, message)`（Win32 需经 `IUserConsentVerifierInterop` 拿工厂）弹 Hello，返回 `Verified` 即通过。
- **依赖**：新增 `windows` crate（WinRT 投影，features：`Security_Credentials`、`Security_Credentials_UI`、`Foundation`、`Win32_System_WinRT`）。项目已用 `windows-sys`，二者可共存。
- **可用性**：Win10 1903+ / Win11 覆盖极广；无 Hello 硬件时 `availability().available = false`，UI 自动隐藏入口、回落密码。
- **失效条件**：换 Windows 用户、Hello 容器被重置、删除该 KeyCredential → `derive` 失败 → 回落密码。

### 5.2 🍎 macOS —— Touch ID + Secure Enclave（路线 B）

- **路线 B（解锁）**：Secure Enclave 私钥 + Keychain 访问控制
  - `SecKeyCreateRandomKey` 建 EC P-256 私钥，属性 `kSecAttrTokenID = kSecAttrTokenIDSecureEnclave`，ACL `SecAccessControlCreateWithFlags(..., .biometryCurrentSet | .privateKeyUsage)`（enroll）。私钥永不出 SE。
  - 解锁时对固定 `challenge` 做 `SecKeyCreateSignature`（ECDSA）——ECDSA 非确定性签名，**不能直接当稳定 KEK 源**。故本平台采用 **ECDH 方案**：登记时同时保存一枚随机对端公钥，解锁时用 SE 私钥与其做 `SecKeyCopyKeyExchangeResult(ecdhKeyExchangeStandard)` 得到**稳定共享密钥** → HKDF → KEK。
  - 使用私钥时系统强制弹 Touch ID（或 Apple Watch）。
  - 备选简化方案：在 Keychain 存一枚随机对称 KEK，item ACL 设 `biometryCurrentSet` + `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`；读取即触发 Touch ID。实现更简单，但 KEK 会短暂出 SE，安全性略低于 ECDH。**首期建议先用备选简化方案，二期升级 ECDH。**
- **路线 A（隐私操作重认证）**：`LocalAuthentication` 的 `LAContext.evaluatePolicy(.deviceOwnerAuthenticationWithBiometrics)`。
- **配置**：`Info.plist` 需 `NSFaceIDUsageDescription`（经 `tauri.conf.json` / 自定义 plist 注入）。
- **失效条件**：`biometryCurrentSet` 在**用户新增 / 删除指纹后自动失效**（这是安全特性）→ 信封解不开 → 回落密码并提示重新登记。

### 5.3 🐧 Linux —— 仅路线 A（便利级，UI 明示降级）

Linux **没有统一的、"每次访问都强制刷指纹"的硬件密钥库**，无法真正做到路线 B。方案：

- **Secret Service（libsecret：GNOME Keyring / KWallet）**：把随机 KEK 存进钥匙串，`biometric.env` 存被该 KEK 包裹的 MK。但钥匙串解锁通常绑登录密码，**指纹只在登录时那一下**，并非每次刷。
- **polkit / fprintd**：只能做路线 A（存在性确认），且官方标注支持不完整，依赖桌面会话跑着 polkit agent，headless/SSH 直接失败。
- **结论**：Linux 上 `availability().strong = false`。设置界面在 Linux 上把该功能标注为**"便利解锁（非硬件级保护）"**，或首期直接不在 Linux 暴露开关。**首期建议：Linux 暂不提供，二/三期视需求再定。**

### 5.4 平台能力矩阵

| 平台 | 解锁（路线 B） | 隐私重认证（路线 A） | 硬件级 | 首期是否实现 |
|---|---|---|---|---|
| Windows | KeyCredentialManager（TPM，RSA 确定性签名） | UserConsentVerifier | ✅ | ✅ 首期 |
| macOS | Secure Enclave（Keychain ACL / ECDH） | LocalAuthentication | ✅ | 二期 |
| Linux | Secret Service（KEK 托管） | polkit/fprintd | ❌ 便利级 | 暂缓 |

### 6.2 解锁页（`app/src/pages/Unlock.tsx`）

- 当 `biometricEnabled && biometricAvailable` 时：
  - **主按钮改为"用指纹解锁"**，页面加载即可自动触发一次（也可点击触发）。
  - 底部保留次级链接："改用访问密码"、"忘记密码？用恢复密钥"。
- 指纹失败 / 取消：不报错打断，平滑回落到密码输入框。

### 6.3 后端命令

```rust
#[tauri::command(async)]
pub fn vault_unlock_biometric(app, state) -> Result<()> {
    // 1. ensure_loaded；读 biometric.env，校验 workspaceId
    // 2. backend::derive(key_ref, challenge)   —— 此处系统弹指纹
    // 3. KEK = HKDF(...); MK = unwrap_with_biometric(env, KEK)
    // 4. vault.unlock_with_master_key(MK)      —— 复用既有入口
    // 5. 与 vault_unlock 完全一致的收尾：reset 限速、grant grace、begin_write_lock、schedule_after_unlock
}
```

- **限速沿用** `state.unlock_guard`：指纹取消不计失败；后端解信封失败才 `record_failure()`。
- 解锁成功后照常触发解锁动画（复用 `vault_unlock` 里 `unlockAnimEnabled` 逻辑）。

### 6.4 与 DPAPI grace 的关系

- 二者独立：可只开指纹、只开 grace、或都开。
- 都开时启动顺序：先试 `vault_try_grace_unlock`（静默、无手势）→ 未命中再由用户触发指纹。避免"开机既走 grace 又弹指纹"的重复打扰。

## 第七部分 · 隐私操作支持指纹（查看 OTP / 私密账户）

### 7.1 现状回顾

查看验证码 / 账密走统一门禁 `ensure_reveal_authorized`（`commands/mod.rs`），窗口内免密、过期则需 `verify_password`；被 `totp_generate_code`、`account_reveal_password` 等复用：

```117:132:app/src-tauri/src/commands/mod.rs
/// 查看 OTP/密码：窗口内可免密；否则必须 verify_password。
pub fn ensure_reveal_authorized(state: &AppState, password: Option<&str>) -> crate::error::Result<()> {
    use crate::error::AppError;
    let minutes = state.config.lock().unwrap().reveal_grace_minutes;
    let now = Instant::now();
    {
        let g = state.reveal_grace.lock().unwrap();
        if let Some(until) = *g {
            if now < until {
                return Ok(());
            }
        }
    }
    let Some(pw) = password.map(str::trim).filter(|s| !s.is_empty()) else {
        return Err(AppError::NeedReauth);
    };
```

### 7.2 新增：指纹作为重认证凭据（路线 A）

新增一个"生物识别重认证"命令，成功后**直接刷新 `reveal_grace` 窗口**（等价于验密成功），复用既有的免密时效：

```rust
#[tauri::command(async)]
pub fn reveal_authorize_biometric(state) -> Result<()> {
    // 前置：vault 已解锁、biometric_enabled
    // backend::verify_presence("确认查看敏感信息")   —— 系统弹指纹（路线 A，无需解 MK）
    // 通过后：按 reveal_grace_minutes 刷新 state.reveal_grace（与 ensure_reveal_authorized 收尾一致）
}
```

前端流程（`Totp.tsx` / `Accounts.tsx` 的取值弹窗）：

1. 调用 `totp_generate_code` / `account_reveal_password`，若返回 `NeedReauth`：
2. 若 `biometricEnabled`：弹"用指纹验证"，成功后调用 `reveal_authorize_biometric`，再重试原调用；
3. 用户也可选"改用密码验证"，走原有 `verify_password` 路径。

> **取回 TOTP 原始密钥**（`totp_reveal_secret`）等最高敏感操作，是否允许指纹替代密码，作为**可配置项**（见 8.1 `biometric_reveal_secret`），默认**仍要求密码**，因为这属于"导出级"操作，风险高于"查看一次性验证码"。

### 8.3 设置界面（`app/src/pages/Settings.tsx`「安全」页签）

在既有「开机免验证 (Windows DPAPI)」卡片旁新增卡片 **「指纹 / 生物识别解锁」**：

- 主开关：`启用指纹解锁`（`biometricUnlockEnabled`）。开启时弹密码确认框（调 `biometric_enable`）。
- `biometric_available == false` 时：开关置灰，提示"本机未检测到可用的指纹 / 人脸 / Windows Hello 硬件"。
- Linux（`strong == false`）：标注"便利解锁（非硬件级保护），主密码 / 恢复密钥仍是你的最终凭据"。
- 子项：`查看验证码 / 账密时允许指纹`（`biometricRevealEnabled`）、`取回 TOTP 原始密钥也允许指纹`（`biometricRevealSecret`，默认关，带风险提示）。
- 状态回显：已登记 / 未登记；换指纹或换机导致失效时给 `callout warn` 提示"指纹凭据已失效，请用密码解锁后重新登记"。

## 第九部分 · 生命周期与边界情形

| 事件 | 处理 |
|---|---|
| 改访问密码（`change_password`） | 指纹信封包裹的是 **MK 不是密码**，**无需失效**，比 grace 更稳（grace 现在会被清）。 |
| 轮换恢复密钥 | 与指纹无关，不受影响。 |
| macOS 新增 / 删除指纹 | `biometryCurrentSet` 自动失效 → `derive` 失败 → 回落密码 + 提示重新登记。 |
| Windows 重置 Hello / 换用户 | KeyCredential 打不开 → 回落密码 + 提示重新登记。 |
| 关闭指纹解锁（disable） | 删硬件密钥 + 删 `biometric.env`，即时生效。 |
| 一键还原（`factory_reset`） | 在既有清理步骤中加入：删硬件密钥、删 `biometric.env`（与 `session::clear()` 并列）。 |
| 换机 / 换工作空间 | `biometric.env` 的 `workspaceId` 不匹配 → 直接忽略并清理，绝不串号。 |
| 硬件临时不可用（外设拔出） | `availability().available=false` → 隐藏入口，静默回落密码，不报错打断。 |
| 连续指纹失败 | 由系统自身节流；应用侧仅在"解信封失败"时计入 `unlock_guard`。 |

## 第十部分 · 安全性论证

1. **at-rest 保护（Win/mac）**：MK 的指纹信封 KEK 来自 TPM / Secure Enclave 中、使用需指纹手势的密钥。攻下 `biometric.env` 文件而无该设备的指纹手势，无法解出 MK —— 达到路线 B。
2. **不扩大云端攻击面**：`biometric.env` 只在本机，永不进 `vault.json` / 云同步。
3. **底座不弱化**：密码（Argon2id）与恢复密钥信封原样保留，指纹只是新增便捷入口；丢设备 / 换机仍靠密码 / 恢复密钥，无单点永久锁死。
4. **登记确权**：`biometric_enable` 强制验密，杜绝他人用自己的生物特征劫持他人 vault。
5. **重认证与解锁分层**：隐私操作走路线 A（MK 已在内存，仅确认在场），不因便捷而降低解锁本身的路线 B 强度。
6. **Linux 诚实降级**：明确告知非硬件级，避免给用户"已受硬件保护"的错误安全感。

## 第十一部分 · 分期实施计划

**第一期（Windows，硬件级）**
1. `biometric/` 模块骨架 + `windows.rs`（KeyCredentialManager 解锁、UserConsentVerifier 重认证）。
2. `vault/envelope.rs` 增 `wrap_with_biometric` / `unwrap_with_biometric`；`biometric.env` 读写。
3. IPC：`biometric_status/enable/disable/vault_unlock_biometric/reveal_authorize_biometric`；`VaultStatus` / `AppConfig` 扩字段。
4. 前端：`Unlock.tsx` 指纹入口、`Settings.tsx` 新卡片、`Totp.tsx`/`Accounts.tsx` 指纹重认证接线。
5. `factory_reset` / `change_password` 生命周期接线。

**第二期（macOS，硬件级）**：`macos.rs`（首用 Keychain ACL 简化方案，后升级 SE + ECDH）；`Info.plist` 注入 `NSFaceIDUsageDescription`。

**第三期（Linux，便利级，可选）**：`linux.rs`（Secret Service 托管 KEK + polkit 重认证），UI 明示降级。

**跨平台库评估**：`robius-authentication` / `tauri-plugin-biometry` 可覆盖路线 A（存在性确认），但**不满足路线 B 的硬件密钥绑定**，故解锁核心仍用平台原生 API；如需快速铺 Linux/隐私重认证，可局部借用其路线 A 能力。

## 第十二部分 · 测试计划

- **单元**：`biometric.env` pack/unpack roundtrip；`workspaceId` 不匹配即拒绝；HKDF→KEK→AEAD roundtrip。
- **Windows 集成**（有 Hello 硬件）：登记→重启→指纹解锁；改密码后指纹仍可用；disable 后文件与密钥被清；重置 Hello 后优雅回落。
- **隐私操作**：`NeedReauth` → 指纹通过 → `reveal_grace` 生效 → 窗口内免验；`biometric_reveal_secret=false` 时取回原始密钥仍要求密码。
- **无硬件回落**：`available=false` 时 UI 无指纹入口、功能完全等价于纯密码流程。
- **限速**：指纹取消不计失败；解信封失败计入 `unlock_guard`。
