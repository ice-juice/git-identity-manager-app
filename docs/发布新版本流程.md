# 发布新版本流程（操作手册）

下次发版按本文走即可。设计原理见 `docs/程序更新功能设计.md`，工作流定义见 `.github/workflows/release.yml`。升级说明数据源是仓库根目录 `CHANGELOG.md`。部分地区访问 GitHub 失败时的代理方案见 `docs/网络代理设置设计.md`。

**仓库：** `ice-juice/git-identity-manager-app`  
**日常开发分支：** `dev`  
**出包 / 打标签分支：** `release`（只认这个分支）  
**`main`：** 不直接出包，也不要在上面打 `v*` 标签

---

## 0. 先搞清三件事

| 动作 | Actions 会做什么 | 客户端能不能检测到更新 |
|---|---|---|
| 只推 `dev` | 不打包 | 不能 |
| 只推 `release` 分支 | **不打包**（避免和打标签各跑一轮） | 不能 |
| 在 `release` 的提交上推送 `vX.Y.Z` 标签 | 三平台打包，创建**草稿** Release，挂上安装包、`.sig`、`latest.json` | 还不能（草稿不是 latest） |
| 手动 Run `Release packages` | 可选抽检出包；勾选 `create_release` 才建草稿 | 视是否 Publish |
| 在 GitHub 上 **Publish** 该 Release（不要标 Pre-release） | `/releases/latest/download/latest.json` 指向新版本 | 能（前提：本机安装版版本号更低） |

GitHub Actions **不会自动改版本号**。版本必须先写进仓库，再推送、再打标签。

默认更新源：

```text
https://github.com/ice-juice/git-identity-manager-app/releases/latest/download/latest.json
```

---

## 1. 标准发版步骤

下面把版本号写成 `X.Y.Z`（例如 `1.1.2`）。标签必须带 `v` 前缀：`vX.Y.Z`。

### 步骤 1 — 在 `dev` 上升版本号、写升级说明并提交

需要改的文件（只改应用自己的版本，不要改依赖里碰巧也是 `1.1.0` 的包）：

| 文件 | 改什么 |
|---|---|
| `CHANGELOG.md` | 在文件顶部（`## [Unreleased]` 之下）新增 `## [X.Y.Z] - YYYY-MM-DD`，按「新增 / 优化 / 修复」写用户能看懂的说明 |
| `app/package.json` | `"version"` |
| `app/package-lock.json` | 顶部 `"version"`，以及 `packages[""].version` |
| `app/src-tauri/tauri.conf.json` | `"version"` |
| `app/src-tauri/Cargo.toml` | `[package] version` |
| `app/src-tauri/Cargo.lock` | `name = "app"` 那一段的 `version` |
| `app/src/pages/Settings.tsx` | `getVersion().catch(() => setVersion("X.Y.Z"))` 的回退值 |

`CHANGELOG.md` 的章节标题必须是 `## [X.Y.Z]`，与即将打的标签 `vX.Y.Z` 对齐。CI 只抽这一节写入 Release 和 `latest.json` 的 `notes`；缺这一节或内容为空时，打标签后的构建会失败。

写法：每条 `- **模块**：做了什么`，面向用户，大约 8–15 条。不要写 commit 哈希或内部文件名。完整约定见 `docs/程序更新功能设计.md` §7.6。

版本怎么加：

- 界面/文案/小修复 → 补丁号，如 `1.1.1` → `1.1.2`
- 新功能 → 次版本号，如 `1.1.1` → `1.2.0`
- 不兼容大改 → 主版本号，如 `2.0.0`

```powershell
cd D:\coding_program\local-git-account-manage
git checkout dev
git pull origin dev
# 改完上面那些文件后：
git add CHANGELOG.md `
  app/package.json app/package-lock.json `
  app/src-tauri/tauri.conf.json `
  app/src-tauri/Cargo.toml app/src-tauri/Cargo.lock `
  app/src/pages/Settings.tsx
git commit -m "chore: 将应用版本升级为 X.Y.Z"
git push origin dev
```

### 步骤 2 — 合并进 `release`、打标签，再一起推送

把「合入 `release`」和「打 `v*` 标签」放在同一次操作里，**先推分支、再推标签**。只推分支不会触发打包；只有推标签才会跑一轮三平台构建并建草稿 Release。不要先推 `release` 再过很久才打标签——中间多一次推送没有收益，也容易忘了打标签。

优先快进。只有 `release` 上有 `dev` 没有的提交时，才需要先处理分叉。

标签是给某一次提交贴的名字，**不会产生新提交**。必须单独推标签，普通 `git push` 不会带上它。

```powershell
git checkout release
git pull origin release
git merge --ff-only dev
git log -1 --oneline
# 确认这一行就是「版本升级为 X.Y.Z」那次提交

git tag -a vX.Y.Z -m "vX.Y.Z <一句话说明>"

# 必须先推分支，再推标签：工作流会检查标签提交已经在 origin/release 上
git push origin release
git push origin vX.Y.Z
```

确认标签钉在同一提交上：

```powershell
git rev-parse vX.Y.Z
git rev-parse origin/release
```

两行哈希应相同。  
**不要**对 `main` 打标签。工作流会拒绝「不在 `release` 历史里」的 `v*` 标签。  
**不要**用 `git push --tags` 把历史标签全推一遍，只推这一个即可。  
**不要**只推标签、不推 `release`：远端 `release` 还停在旧提交时，标签检查会失败。

如果只想出安装包、暂不建 Release，到 Actions 手动 Run `Release packages`（不要勾 `create_release`），不要为了抽检再推一次空的 `release`。

### 步骤 3 — 等 Actions 跑完

打开：  
https://github.com/ice-juice/git-identity-manager-app/actions

看由 **`vX.Y.Z`** 触发的 `Release packages`。Windows / macOS / Linux 都要成功。

失败常见原因：签名 Secrets 缺失或填错（`TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`）。

### 步骤 4 — 检查草稿 Release，再 Publish

打开：  
https://github.com/ice-juice/git-identity-manager-app/releases

点进草稿 `vX.Y.Z`，确认大致有：

- Windows：`git-account-manager_X.Y.Z_x64-setup.exe` 和 `.exe.sig`
- macOS：`git-account-manager_universal.app.tar.gz` 和 `.sig`
- Linux：`git-account-manager_X.Y.Z_amd64.AppImage` 和 `.sig`
- `latest.json`（里面的 `"version"` 必须是 `X.Y.Z`，且含 `windows-x86_64`）
- Release 正文和 `latest.json` 的 `"notes"` 都等于 `CHANGELOG.md` 里 `## [X.Y.Z]` 那一节（不要只在网页上改描述——改了网页，客户端仍读 `latest.json`）

确认后点 **Publish release**。

- 不要只留 **Draft**
- 不要勾 **Pre-release**（默认源走 `/releases/latest/`，pre-release 不会成为 latest）

发布后用浏览器打开，应能下到 JSON：

```text
https://github.com/ice-juice/git-identity-manager-app/releases/latest/download/latest.json
```

### 步骤 5 — 用「旧安装版」测应用内更新

本机必须装着 **比 X.Y.Z 更低** 的 NSIS 安装版（例如刚发 1.1.2 时，用已安装的 1.1.1）。

不要用：

- `npm run tauri dev`
- 本机刚编的未安装 `app.exe`
- 已经是 `X.Y.Z` 的安装版（版本相同，不会提示更新）

操作：

1. 打开旧版本 → 解锁工作空间
2. **设置 → 关于与更新**
3. 更新源保持默认 GitHub 仓库
4. **立即检查更新** → 应看到 `X.Y.Z`，以及与 CHANGELOG 该节一致的升级说明
5. **下载并安装** → 重启后设置里版本应为 `X.Y.Z`

也可测启动自动检查：打开自动检查，完全退出再开，约 5 秒后右下角应弹出更新提示。

如果以前点过「跳过此版本」，先看 `%APPDATA%\git-account-manager\config.json` 里的 `skipped_update_version`，测自动提示前把它清掉。

## 2. 一页检查清单

发版当天按这个勾：

- [ ] `dev` 上功能已合入、工作区干净
- [ ] 六个版本位置都改成同一 `X.Y.Z`，`CHANGELOG.md` 已有 `## [X.Y.Z]` 且内容面向用户，并已提交、推送到 `dev`
- [ ] `dev` 已快进合并进 `release`，打了 `vX.Y.Z`，并按顺序推送了 `release` 和该标签（只触发一轮构建）
- [ ] Actions 三平台绿灯
- [ ] 草稿 Release 附件齐全，`latest.json` 版本正确，`notes` 与 CHANGELOG 该节一致
- [ ] 已 Publish，且不是 Pre-release
- [ ] 浏览器能打开 `/releases/latest/download/latest.json`
- [ ] 旧安装版能检查到更新、能下载安装、重启后版本正确
- [ ] （可选）把 `release` 上多出来的提交再同步回 `dev`，保持两边一致

## 3. 版本提交漏在 `release` 上时

如果版本号是在 `release` 上改的、`dev` 还停在旧版本：

```powershell
git checkout dev
git pull origin dev
git merge --ff-only release
git push origin dev
```

以后按「步骤 1 先在 `dev` 升版本」做，一般不需要这步。

---

## 4. 不要做的事

| 错误 | 后果 |
|---|---|
| 以为推 `release` 就会自动升版本、自动打包或发更新 | 版本不变；只推分支现在也不打包；旧客户端看不到更新 |
| 先推 `release`、隔很久再打标签 | 多一次来回，容易忘标签；应合并、打标签后立刻按顺序推送 |
| 只打标签、不 Publish 草稿 | `/releases/latest/` 仍指向上一版 |
| 把 Release 标成 Pre-release | 默认源读不到 |
| 对 `main` / 旧提交打 `v*` | CI 直接失败 |
| 用 `tauri dev` 或未安装的 exe 测「下载并安装」 | 检查或许能出结果，安装/重启通常不完整 |
| 用已经是新版本的安装包去测更新 | 永远提示已是最新 |
| 换一把更新签名私钥，却没改客户端内置公钥 | 旧客户端安装会被拒 |
| 升版本却不写 `CHANGELOG.md` 的 `## [X.Y.Z]` | 打 `v*` 后 CI 直接失败 |
| 只在 GitHub 网页改 Release 描述，不改 `CHANGELOG.md` / 不重传 `latest.json` | 网页上看着有说明，应用内 `notes` 仍是旧的或空的 |

## 5. 网页备选：只建标签

不想用命令行打标签时：

1. 打开仓库 Tags / Releases
2. 新建 tag：`vX.Y.Z`
3. **Target 必须选 `release`**，且指向已升版本的那次提交
4. 只创建 tag，让 Actions 去建草稿 Release
5. 等构建完成后再 Publish

命令行更不容易选错 Target，优先用第 1 节步骤 2。若网页建标签前远端 `release` 还没有新提交，先把 `release` 推上去（不会触发打包），再创建 tag。

## 6. 一次性环境（已配好则跳过）

仓库 **Settings → Secrets and variables → Actions** 必须已有：

- `TAURI_SIGNING_PRIVATE_KEY`
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`

公钥已写入 `app/src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey`。  
这把密钥全平台共用；换密钥等于切断旧客户端的更新校验。
